# Journal des modifications

## 0.9.9 — « Correctif : l'IPAM se rafraîchit après un import »
- Après un import NetBox (ou une découverte réseau, ou l'annulation d'un import), seuls les VLAN apparaissaient dans l'IPAM : les onglets Réseaux, Adresses, Pools et Espaces gardaient l'état d'avant l'import jusqu'au rechargement de la page. Les assistants préviennent maintenant la page, qui recharge toutes ses listes.
- Numérotation : suite en 0.9.10 (traçabilité) … DHCP multi-espaces en 0.9.14.

## 0.9.8 — « Vues DNS »
- **Vues DNS** (page DNS, onglet « Vues ») : un même nom de zone peut recevoir des réponses différentes selon le client (`match-clients`, éventuellement `match-destinations`), avec ou sans récursion par vue. Listes de clients validées élément par élément (`any`, `none`, `localhost`, `localnets`, adresse, réseau, négation `!`), 50 éléments et 16 vues au plus ; **la première vue dont la liste correspond répond** (ordre réglable, avertissement quand une vue est masquée par une vue « any » placée avant).
- **Règle** : sans vue, la configuration est exactement celle d'avant. Dès qu'une vue existe, **toute zone appartient à une vue** (BIND n'admet pas de zone hors vue) : la première vue reprend explicitement les zones existantes (confirmation), la création d'une zone exige une vue, et le rendu revérifie la règle. Supprimer la dernière vue rend ses zones ordinaires (confirmation). Fichiers `db.<vue>.<zone>` ; **copie d'une zone vers une autre vue** avec ses enregistrements (point de départ d'une vue « externe »). Les modifications de zone sans `view_id` laissent la zone dans sa vue.
- **Filtrage (RPZ)** : la zone de politique est déclarée dans **chaque** vue, un fichier par vue (`db.rpz-<vue>`).
- **Cluster** : une **clé de transfert par vue** (`ddi-xfr-<vue>`), dérivée par HMAC-SHA256 du secret du cluster et du nom de la vue : les deux nœuds la calculent à l'identique, **rien de nouveau à distribuer**. Le primaire range chaque transfert signé dans la bonne vue (`key "ddi-xfr-V"; !key "ddi-xfr-AUTRE"; …`), envoie ses NOTIFY avec la clé de la vue ; le secondaire demande chaque zone avec la clé de sa vue. Les clés sont dans `/etc/bind/ddi-xfr-views.key` (0640 root:bind, écrites par root, incluses par les options, retirées quand il n'y a plus de vue, sauvegardées avec le retour arrière). Promotion, réintégration et retour arrière automatique fonctionnent par vue. **Tous les nœuds doivent être en 0.9.8** pour utiliser des vues.
- **Garde-fou** : le serveur doit se résoudre lui-même — si aucune vue ne répond à 127.0.0.1 et ::1, le déploiement est refusé avec le motif.
- Points de restauration et import/synchronisation (NetBox, AD) tiennent compte des vues ; le journal des requêtes accepte le préfixe « view <nom>: » de BIND.
- **Limites** : les mises à jour dynamiques de Kea (DDNS) vont à la vue qui correspond à l'adresse de l'expéditeur ; `localhost` couvre **toutes** les adresses du serveur (utiliser des adresses explicites pour séparer un client local).
- Correctif : une adresse IP seule (sans `/32`) dans une liste de clients ne correspondait jamais (repéré par les tests).
- Tests : `unit-views` (12), `e2e-iter13` (11), `tests/b23-bind-views-live.sh` (64 contrôles, deux vrais BIND : réponses par client, clé par vue, AXFR/NOTIFY, RPZ par vue, promotion, retour sans vue, refus sans effet).
- Numérotation : suite en 0.9.9 (traçabilité) … DHCP multi-espaces en 0.9.13.

## 0.9.7 — « Correctif : jeton NetBox collé avec « Token » »
- NetBox affiche le jeton sous la forme « Token xxxxxxxx » : quand ce texte était collé tel quel, la console envoyait « Token Token xxxxxxxx » et NetBox répondait « Invalid authorization header ». Le mot « Token » (ou « Bearer ») collé devant le jeton est maintenant retiré, aussi pour un jeton déjà enregistré.
- Tests : `unit-iter4` (+1 assertion).
- Numérotation : vues DNS en **0.9.8** (le reste décalé d'un cran, DHCP multi-espaces en 0.9.13).

## 0.9.6 — « Correctif : jetons NetBox v2 »
- **Jetons d'API NetBox 4 (v2)** : un jeton de la forme `<clé>.<jeton>` (avec ou sans préfixe `nbt_`) était envoyé avec l'en-tête `Token`, que NetBox refuse (« Invalid authorization header: Must be in the form "Bearer <key>.<token>" or "Token <token>" »). La console envoie désormais `Bearer` pour ces jetons et `Token` pour les jetons v1 (40 caractères).
- Tests : `unit-iter4` (en-tête selon le format du jeton).
- Numérotation : vues DNS en **0.9.7** (le reste décalé d'un cran, DHCP multi-espaces en 0.9.12).

## 0.9.5 — « Correctif : messages d'erreur des assistants »
- **Les assistants n'affichaient jamais leurs erreurs** : le cadre commun des assistants (`WizardShell`) ne rendait que les étapes ; l'alerte d'erreur de l'assistant NetBox (et celle de l'assistant Active Directory) était donc invisible — l'erreur n'apparaissait que dans la console du navigateur. Le cadre rend maintenant ce contenu commun : le test NetBox affiche « NetBox refuse le jeton… » avec le motif donné par NetBox.
- Courbes (page Filtrage) : les heures de l'axe ne sont écrites qu'une fois la page montée dans le navigateur (écart d'hydratation entre serveur et navigateur).
- Tests : `unit-session` (+1).
- Numérotation : vues DNS en **0.9.6** (le reste décalé d'un cran, DHCP multi-espaces en 0.9.11).

## 0.9.4 — « Correctif intercalaire : source NetBox »
- **Le test de connexion NetBox dit pourquoi** : quand NetBox refuse le jeton, la console relaie désormais le **motif donné par NetBox** (statut HTTP et message, par exemple « Invalid v1 token », « Token expired » ou « Invalid source IP »), nettoyé (texte brut, sans caractère de contrôle, 160 caractères au plus) et affiché sous le bouton. Le jeton est aussi **nettoyé** (espaces et retour à la ligne collés avec lui) côté interface et côté serveur.
- Tests : `unit-iter4` (+1 : motif conservé, texte hostile), `e2e-iter4` (motif transmis à l'interface, jeton collé avec espaces).
- Numérotation : la série 0.9.x se poursuit avec les vues DNS en **0.9.5** (le reste est décalé d'un cran, DHCP multi-espaces en 0.9.10).

## 0.9.3 — « Test de bascule guidé avec rapport »
- **Correctif — bouton « Test » de la source NetBox** : quand NetBox refusait le jeton, la console renvoyait ce refus en **401** et l'interface le prenait pour une session expirée : l'utilisateur était **déconnecté** et ne voyait jamais le résultat du test (même chose pour l'aperçu). Le refus d'un service tiers sort désormais en **502** (`netbox_auth`, message : « NetBox refuse le jeton… Si un jeton est enregistré, saisissez-le de nouveau »), et l'interface ne renvoie à la connexion que pour l'absence de session (`unauthenticated`, règle isolée dans `app/utils/session.ts`). Tests : `unit-session` (5), `e2e-iter4` mis à jour (502 attendu).
- **Test de bascule** (`ddibuntu-cluster drill-check | drill --yes [--candidate N] [--back] [--json] | drills | drill-clear --yes`, ou carte « Test de bascule » de la page Cluster) : une **vraie bascule du primaire PostgreSQL**, mesurée de bout en bout, puis — sur demande — le **retour au primaire d'origine**, lui aussi mesuré. Un moniteur indépendant (`cluster-drill.py`, bibliothèque standard seulement, aucun secret) échantillonne l'API Patroni de **chaque** nœud de données (TLS mutuel) toutes les 0,5 s et mesure : **fenêtre sans primaire**, **promotion** du nouveau primaire, **rétrogradation**, **réintégration** de l'ancien primaire (réplica, même ligne de temps, réplication continue), **rattrapage** de la réplication, **ligne de temps** (+1 exactement), **continuité de la position WAL** (aucune perte) et retard maximal ; puis des contrôles après coup (primaire attendu, secondaires, quorum etcd non dégradé, Kea HA, adresse virtuelle). Chaque mesure a un verdict conforme / à surveiller / en écart selon des seuils inscrits dans le rapport ; la précision (échantillonnage) y est indiquée. Mesuré sur un vrai cluster Patroni + etcd en boucle locale : environ 3 s sans primaire, promotion 3,5 s, réintégration 5,5 s, rattrapage 2 s.
- **Pré-contrôles** (aussi en lecture seule : `drill-check`) : deux nœuds de données joignables et un seul primaire, Patroni non en pause et aucune bascule déjà planifiée, candidat en réplication continue (jamais le primaire ni l'arbitre), retard borné, autres secondaires sains, aucun redémarrage en attente, quorum etcd avec voix saines, aucun autre test en cours ; Kea HA, adresse virtuelle et services sont examinés quand ils existent. **Un contrôle en écart refuse le test : aucune bascule n'est tentée** et le refus est lui-même conservé comme rapport.
- **Rapport conservé dans le cluster** : JSON versionné (≤ 100 Ko) déposé dans etcd (`/ddibuntu-cluster/drills/<horodatage>`, **20 derniers**), donc visible depuis tous les nœuds et survivant à la perte de celui qui l'a produit ; publié pour la console (10 derniers). Contenu : pré-contrôles, mesures et verdicts par phase, contrôles après coup, chronologie horodatée des événements (commande, plus de primaire, promotion, rétrogradation, réintégration…), seuils, durée ; téléchargeable en JSON.
- **Un test à la fois, et la topologie ne bouge pas pendant ce temps** : verrou local et marque etcd « test en cours » (20 minutes de validité, retirée par le piège de sortie **uniquement si elle porte l'identifiant du test**, y compris après un arrêt par signal). Pendant le test sont refusés : `change-ip`, `remove-node`, `recover`, `take-ca`, `set-net`, la bascule manuelle et un second test — **sans toucher à la marque du premier** (défaut de conception repéré et corrigé en cours de route : un second test écrasait la marque du premier). Le verrou de nœud est rendu avant le test : la synchronisation et le suivi de Kea/BIND continuent pendant la bascule, comme lors d'une vraie panne. Nœud disparu en plein test : la marque expire seule, `drill-clear --yes` la retire tout de suite.
- **Console** (administrateur, sur la console du primaire ; lecture seule ailleurs) : historique des rapports, fenêtre maison en trois temps — **pré-contrôles avec spinner**, confirmation (retaper le nom du cluster, retour au primaire d'origine coché par défaut, avertissement sur l'indisponibilité en écriture de quelques secondes), **avancement en direct** (étape, temps écoulé ; la fenêtre peut être fermée, le test continue) — puis rapport détaillé (mesures et verdicts, contrôles après coup, chronologie, seuils, précision, téléchargement). Bandeau « test en cours » pour les autres administrateurs. Textes FR/EN.
- **Frontière de privilèges** : `.cluster-action` accepte `drill-check` (clés `action`, `node` facultatif) et `drill` (`action`, `confirm` = nom du cluster, `node`, `back` booléen) ; root relit le JSON (≤ 1 Ko) avec un **jeu de clés exact**, refuse `back` non booléen, nom piégé, clé supplémentaire, lien symbolique, fichier tronqué. L'API refuse avant dépôt (409 : `confirm_mismatch`, `invalid_candidate`, `quorum_required`, `cluster_state_stale`, `drill_active`) ; les fichiers publiés par root (rapports, pré-contrôles, avancement) sont relus champ par champ et bornés, un statut inconnu vaut « en écart », jamais « conforme ».
- **Installation** : `cluster-drill.py` fait partie des fichiers vérifiés par l'installateur.
- Tests : `b22-cluster-drill-live.sh` (**104 contrôles** sur 3 etcd + 2 Patroni/PostgreSQL réels : pré-contrôles, refus motivés — Patroni en pause, secondaire arrêté —, historique plafonné à 20 sans toucher aux clés étrangères, bascule réelle sans retour puis avec retour, aucune donnée perdue, refus de toutes les opérations de topologie pendant un test y compris par la console, demandes hostiles de la console, arrêt par signal en pleine bascule, marque abandonnée), `unit-drill` (10 tests : relecture des rapports, valeurs hostiles, marque et avancement), `unit-cluster` (+3 tests : refus préalables du test et pendant le test), `e2e-iter12` (**14 tests** de l'API sur le serveur construit : droits, validation stricte, refus 409, fichiers piégés, téléchargement, audit), régression complète au vert.
- **Limites connues** : les mesures de b22 se font en boucle locale (temps de Patroni, pas d'un vrai réseau) — elles sont **à refaire au premier laboratoire**, de même que le comportement des clients DHCP/DNS pendant la fenêtre sans primaire et le suivi de l'adresse virtuelle sur de vraies interfaces ; la précision est celle de l'échantillonnage (0,5 s) et l'écriture applicative n'est pas simulée (la sonde « primaire » de Patroni fait foi) ; la vue `/cluster` de Patroni (et donc la page Cluster) garde l'ancien état de l'ex-primaire jusqu'à une dizaine de secondes après la bascule, alors que le moniteur lit l'état réel de chaque nœud ; pendant le test la console du primaire sortant passe brièvement en lecture seule (le résultat se lit sur le nouveau primaire si le test est lancé sans retour) ; le test se lance depuis un nœud de données et exige deux nœuds de données sains ; deux lancements simultanés depuis deux nœuds restent protégés par la marque etcd seulement (fenêtre de quelques millisecondes entre lecture et écriture).

## 0.9.2 — « Réglages du cluster : adresse virtuelle, réseau dédié, certificats, adresse d'un nœud »
- **Adresse virtuelle et réseau dédié modifiables à chaud** (`ddibuntu-cluster set-vip | clear-vip | vip-iface | set-net | settings`) : les réglages communs sont publiés **une seule fois** dans etcd (JSON ≤ 1 Ko, révision croissante) et **chaque nœud les applique seul** à sa prochaine synchronisation, arbitre compris ; l'interface qui porte la VIP reste **propre à chaque nœud** (si elle n'existe pas sur un nœud, il le dit avec la commande de correction et réessaie, sans rien casser). `set-net` est refusé si un nœud est hors du réseau annoncé ; les accès de réplication de Patroni suivent le réseau. Valeurs piégées dans etcd (JSON invalide, clés inconnues, types ou bornes hors plage, adresses hostiles) ignorées.
- **Renouvellement des certificats sans interruption** (`renew-cert [--force] [--wait N]`, `sign-requests`, `cert-status`) : le nœud crée **sa clé et sa demande**, la clé **ne quitte jamais le nœud** ; seule l'autorité signe, et seulement une demande conforme (nom au registre, adresse du registre ou d'un déplacement annoncé, sujet exact, EC P-256, sans extension ni attribut — les adresses du certificat viennent du registre) ; le nœud n'installe qu'un certificat signé par l'autorité, correspondant à sa clé et à sa demande (un certificat d'une autre autorité, forgé ou destiné à une autre demande est refusé et journalisé). **etcd recharge le certificat à chaque connexion : aucun redémarrage.** **Renouvellement automatique** à 60 jours de l'échéance (`DDI_RENEW_DAYS`), une demande à la fois, nouvelle tentative au bout d'une heure ; les trois derniers certificats sont conservés (sans clé). Le nœud porteur de l'autorité renouvelle le sien de la même façon.
- **Changement d'adresse d'un nœud** (`change-ip --ip NOUVELLE --yes`, depuis le nœud lui-même) : annonce du déplacement, certificat valable pour l'ancienne **et** la nouvelle adresse, **ouverture préalable du pare-feu des autres nœuds à la nouvelle adresse (réseau dédié seulement) avec accusés de réception — le nœud n'avance qu'après tous les accusés, sinon annulation sans trace (sans cela etcd aurait été coupé de ce nœud par le pare-feu de production, défaut découvert en cours de route)**, mise à jour du membre etcd, réécriture d'etcd/Patroni/Keepalived/pare-feu, redémarrage d'etcd, inscription au registre ; les autres nœuds s'alignent **seuls** et seulement si l'annonce est récente, cohérente avec le registre et l'ancienne adresse connue (une réécriture du registre sans annonce, une annonce périmée, datée du futur ou visant une adresse inconnue est ignorée). **Retour arrière complet** si etcd ne redémarre pas sur la nouvelle adresse ; abandon propre sans trace si l'autorité ne signe pas à temps. Refus : primaire PostgreSQL en place (basculer d'abord), quorum sans marge, adresse prise, hors du réseau dédié, non portée par le serveur. Validé sur **les trois types de nœuds** (arbitre, données, autorité) avec de vrais etcd.
- **Verrou de nœud** (`flock`) : une seule opération qui modifie la configuration à la fois. Découvert grâce à ce travail : la synchronisation automatique (chaque minute) aurait pu réécrire l'ancienne adresse pendant un changement d'adresse de plusieurs minutes. Les minuteries ne l'attendent pas (elles reviennent à la minute suivante), les demandes d'un administrateur attendent leur tour.
- **Console** (page Cluster, administrateur) : cartes « Adresse virtuelle et réseau dédié » (valeur publiée, état d'application révision par révision), « Certificats » (jours restants du nœud et de l'autorité, demande en cours, renouvellement immédiat) et « Adresse de ce nœud » ; modales maison avec confirmation à retaper (nom du cluster, nom du nœud pour le changement d'adresse) et spinner pendant l'attente du résultat de root ; interfaces proposées d'après le serveur.
- **Frontière de privilèges** : `.cluster-action` accepte `set-vip`, `clear-vip`, `vip-iface`, `set-net`, `renew-cert`, `change-ip` ; root relit le JSON (≤ 1 Ko) avec un **jeu de clés exact par action**, confirmation identique, VRID entier 1–255 (booléens et texte refusés), adresses et interfaces validées, lien symbolique et demande tronquée refusés ; rien n'est traité sur l'arbitre. L'API refuse avant dépôt ce qui contredit l'état publié (409 : `vip_is_node`, `no_vip`, `nodes_outside_net`, `renew_pending`, `same_ip`, `node_ip_taken`, `ip_outside_net`, `is_leader`, `quorum_margin_required`, `iface_unknown`, `ip_not_local`, `quorum_required`…).
- **État du cluster** : `settings` (publié / appliqué) et `pki` (jours restants, demande en cours) dans `cluster-status.json` ; l'alerte `node.cert_expiry` (0.9.1) se résout d'elle-même après un renouvellement.
- **Correctifs** : `render_keepalived` ne laisse plus de configuration quand l'adresse virtuelle est retirée ; l'adresse virtuelle ne peut pas être celle d'un nœud.
- Tests : `b21-cluster-settings-live.sh` (**309 contrôles** sur 3 etcd réels en TLS mutuel : réglages et valeurs piégées, certificats dont demandes hostiles et certificat forgé, renouvellement automatique, changement d'adresse des trois nœuds, retour arrière, annonces hostiles, verrou, demandes de la console), `unit-cluster` (12 tests dont les refus préalables et l’analyse des nouveaux blocs), `e2e-iter11` (**13 tests** de l’API : validation stricte, refus 409, demandes déposées, traductions), régression complète au vert.
- **Limites connues** : le certificat de l'**autorité** (10 ans) n'est pas renouvelé automatiquement ; le comportement de Patroni lors d'un changement d'adresse sur un vrai nœud de données (redémarrage du service) et celui de VRRP en unicast après changement d'adresse restent **à vérifier au premier laboratoire** ; `change-ip` se lance depuis le nœud concerné (la console ne le fait que pour le nœud sur lequel elle tourne) et doit être précédé d'une configuration de la nouvelle adresse sur le serveur ; **tous les nœuds doivent être en 0.9.2** pour qu'un changement d'adresse aboutisse (un nœud plus ancien n'accuse pas réception : l'opération est annulée sans rien modifier et nomme le nœud) ; un nœud du cluster (certificat valide) peut faire ouvrir le pare-feu des autres à une adresse de son choix **dans le réseau dédié** pendant au plus un jour (les ports restent protégés par le TLS mutuel) ; un nœud arrêté pendant un déplacement ne s'aligne à son retour que si l'annonce a moins d'un jour ; le re-rendu de BIND secondaire et de Kea HA (générés par la console du leader) après un changement d'adresse reste **à vérifier au premier laboratoire**.

## 0.9.1 — « Alertes et supervision, tableau de bord vivant, correctif de la page Cluster »
- **Correction de la page Cluster** (« Erreur interne » sur un serveur encore seul, 0.9.0 et antérieures) : la console, très restreinte par systemd, n'avait pas le droit d'interroger le noyau sur les interfaces réseau (`AF_NETLINK` absent de `RestrictAddressFamilies`) ; l'énumération des adresses du serveur échouait (errno 97) et l'API répondait 500. L'unité autorise maintenant `AF_NETLINK` (lecture seule : aucune capacité réseau d'administration, `CAP_NET_ADMIN` reste exclu), l'énumération ne peut plus faire échouer l'API, l'interface virtuelle devient un champ libre quand la liste des adresses est inconnue, et la vérification de référence « l'adresse est bien portée par ce serveur » est faite par `ddibuntu-cluster init` (root).
- **Santé de chaque nœud** (`ddibuntu-health`, minuteur toutes les minutes, root, lecture seule, aucun secret) : services attendus (console, DNS, DHCP, pare-feu, Keepalived, heure, etcd, Patroni), PostgreSQL, disques, échéances des certificats (console, autorité et nœud du cluster), synchronisation de l'heure, charge, mémoire. Publiée dans `/run/ddibuntu/health.json` ; **dans un cluster, chaque nœud, l'arbitre compris, la dépose aussi dans etcd** (`/ddibuntu-cluster/health/<nœud>`, 4 Kio maximum, clé = nom du nœud) : la console du leader voit donc tout le cluster. Valeurs piégées (JSON invalide, démesurées, nom différent de la clé) ignorées à la relecture.
- **Moteur d’alertes** (console accessible en écriture : leader ou serveur seul ; les réplicas ne l’exécutent pas) : 23 règles couvrant le cluster (état périmé, quorum perdu ou sans marge, membre hors service, absence de leader, etcd malsain, retard et état des réplicas, changement de leader, adresse virtuelle non portée), les nœuds (santé périmée, service arrêté, PostgreSQL arrêté, disque plein, certificat proche de l'échéance, heure non synchronisée, mémoire basse), les sauvegardes (état périmé, aucune sauvegarde, trop ancienne, archivage en échec, dernière exécution en échec) et l'IPAM (sous-réseau presque plein). Une alerte s'ouvre dès le constat, **se résout seule** après des évaluations consécutives sans le problème, remonte de gravité (et renotifie) quand elle s'aggrave. Évaluation toutes les minutes, transactionnelle (verrou consultatif : aucun doublon même avec deux consoles), purge automatique (résolues 90 jours, envois 30 jours).
- **Mise en silence** (opérateur) par alerte, par règle, par nœud ou par sujet, avec durée et motif : plus aucune notification, l'alerte reste visible.
- **Notifications** (administrateur) : **webhook** JSON (HTTP/HTTPS seulement, sans identifiants dans l'URL, adresses de métadonnées refusées, redirections non suivies, signature HMAC-SHA256 facultative dans `X-DDIbuntu-Signature`) et **e-mail** par un client SMTP écrit pour l'occasion (STARTTLS, TLS implicite ou clair ; **jamais d'authentification sans chiffrement** ; protection contre l'injection d'en-têtes). Gravité minimale, rappel périodique, 5 tentatives par envoi avec journal des envois, boutons « Tester » ; les secrets (mot de passe SMTP, clé de signature) sont chiffrés en base (AES-256-GCM) et jamais renvoyés par l'API.
- **Exportateur Prometheus** `GET /api/metrics` : jeton `ddm_…` créé, remplacé ou révoqué par l'administrateur (affiché une seule fois, seule son empreinte SHA-256 est conservée, accepté en en-tête `Authorization: Bearer` uniquement) ; métriques du cluster, du quorum, du leader, du retard de réplication, de chaque nœud (services, disques, certificats, charge), des sauvegardes, des sous-réseaux et des alertes ouvertes.
- **Console** : nouvel onglet Système › Alertes (alertes ouvertes avec mise en silence, silences actifs, historique, envois, formulaire des notifications et seuils, jeton Prometheus). Seuils par défaut : disque 85 % / 95 %, certificats 30 / 7 jours, retard 64 Mio, sous-réseaux 90 % / 98 %.
- **Tableau de bord évolué** : actualisation automatique toutes les 30 s (avec l'heure de dernière actualisation), bandeau d'alertes par gravité (les plus importantes listées, accès direct à Système › Alertes), cartes « Services de ce nœud » (état de chaque service, PostgreSQL, heure, échéance du certificat), « Cluster » (leader, quorum et pannes tolérables, adresse virtuelle, chaque nœud avec son rôle et ses anomalies) et « Sauvegardes » (dernière sauvegarde, fenêtre restaurable, archivage), en plus des compteurs, du système, des sous-réseaux et des types. ## 0.9.0 — « Sauvegarde de la base et restauration à un instant donné (PITR) »
- **Sauvegardes complètes + archivage continu des journaux de transactions (WAL)** : `ddibuntu-backup` prend une sauvegarde `pg_basebackup` compressée, vérifiable (SHA-256) et horodatée, pendant que `archive_command` (`wal-archive.sh`) compresse et range chaque journal (idempotent, refuse d'écraser un journal différent, valide les noms). On peut ramener la base à **n'importe quel instant de la fenêtre restaurable**, à la dernière sauvegarde, au plus récent possible ou à l'état exact d'une sauvegarde.
- **Planification** (`ddibuntu-backup.timer`, toutes les 15 minutes) : première sauvegarde à l'activation, puis une par intervalle (24 h par défaut, pas avant l'heure de début), **et aussitôt après un changement de timeline** (bascule du cluster ou restauration). Rétention : N sauvegardes complètes conservées (1 à 30, 3 par défaut) ; les journaux plus anciens que la plus ancienne sauvegarde conservée sont supprimés. Copie externe optionnelle (dossier d'un volume monté : NFS, disque…) synchronisée après chaque passage. La dernière sauvegarde ne peut jamais être supprimée.
- **Restauration** (`ddibuntu-backup restore --at "AAAA-MM-JJ hh:mm:ss+00" | --latest | --id ID --yes`) : choisit la dernière sauvegarde antérieure à la cible, rejoue les journaux jusqu'à l'instant visé et promeut sur une **nouvelle timeline** (les branches antérieures restent atteignables). L'ancienne base est conservée à côté (`main.pre-restore.<date>`, 14 jours), **retour automatique à la base précédente en cas d'échec** (journal manquant, cible hors fenêtre…), nouvelle sauvegarde de référence prise ensuite. Un message d'échec propose `--latest` quand la cible n'est suivie d'aucune activité archivée.
- **Dans un cluster** (nœud primaire seulement) : Patroni est mis en pause, la base est remplacée **sans changer de leader**, puis Patroni reprend et chaque secondaire est recréé depuis le primaire (`reinit`). Les paramètres (rétention, intervalle, heure, copie externe, activation) sont **partagés par etcd** ; chaque nœud de données a son dépôt local, un secondaire met à niveau son archivage tout seul (rendu Patroni + redémarrage planifié) et l'arbitre n'a rien à sauvegarder. Après une bascule, le nouveau primaire prend sa propre sauvegarde complète.
- **Console** (Système › Sauvegardes, administrateur ; lecture par l'opérateur) : état (activation, rôle, archivage des journaux avec alerte sur échecs, fenêtre restaurable, espace libre, copie externe), catalogue des sauvegardes (vérifier, supprimer, restaurer), sauvegarde immédiate, rétention, vérification d'intégrité, réglages, **restauration à un instant précis** (heure locale convertie en UTC) ou au plus récent, avec confirmation à retaper (nom du cluster, ou de la machine hors cluster), suivi des phases (le panneau survit à la coupure de la console et à un rechargement de page) et boutons suspendus pendant une restauration. Spinner partout, modales maison.
- **API** : `GET /api/backup/status` (opérateur), `POST /api/backup/refresh` (opérateur), `POST /api/backup/action` (`run|verify|prune|enable|disable|delete`), `POST /api/backup/configure`, `POST /api/backup/restore` (administrateur) ; refus 409 explicites contre l'état publié (`backup_primary_only`, `backup_witness`, `backup_last`, `confirm_mismatch`, `time_in_future`, `time_before_first_backup`, `restore_in_progress`…), une seule demande en attente (`action_pending`), audit `backup.*`.
- **Frontière de privilèges** : la console ne sauvegarde ni ne restaure jamais ; elle dépose `.backup-request` (≤ 600 octets) que root relit strictement (JSON, clés connues par action, identifiants et dates validés, confirmation identique, lien symbolique et fichier non régulier refusés). `backup.conf` est relu par expressions régulières, jamais exécuté. Verrou unique (`flock`) contre les opérations simultanées.
- **Installation et mise à jour** : units, configuration `conf.d` de PostgreSQL, dépôt `/var/lib/ddibuntu/backup` propriété de `postgres`, paramètres `archive_mode`/`archive_command` rendus dans la configuration Patroni. Sur une appliance existante, l'archivage ne démarre qu'à l'activation (Système › Sauvegardes › « Activer les sauvegardes ») : PostgreSQL redémarre une fois (en cluster : redémarrage en attente de chaque nœud par Patroni).
- Tests : `b18-backup-live.sh` (**156 contrôles sur une vraie base PostgreSQL 16** : archivage dont noms hostiles, deux sauvegardes, corruption détectée, restauration à T_A / T_B / T_C sur des branches de timelines successives, `--latest`, `--id`, demandes impossibles, échec avec retour automatique, rétention, minuteur avec horloge simulée, copie externe, 25 demandes JSON hostiles dont lien symbolique, arbitre), `b19-backup-cluster-live.sh` (**76 contrôles avec de vrais Patroni + etcd** : paramètres Patroni, réglages partagés par etcd, valeur etcd piégée ignorée, restauration au primaire avec secondaire recréé, échec avec retour, chemin de mise à niveau d'un secondaire sans archivage, bascule puis sauvegarde du nouveau primaire), `unit-backup.test.ts` (13), `e2e-iter9.test.ts` (16) ; interface vérifiée dans un navigateur automatisé.
- **Limites connues** : chaque nœud de données a **son propre dépôt** : après une bascule, la fenêtre restaurable du nouveau primaire repart de sa première sauvegarde (un dossier partagé en « copie externe » permet de conserver les journaux de l'ancien) ; l'instant visé doit être suivi d'une activité archivée (sinon PostgreSQL ne peut pas conclure : utiliser « le plus récent ») ; en cluster, une restauration à un instant recrée les secondaires (plusieurs minutes de réplication) ; les tablespaces ne sont pas pris en charge (refusés) ; la restauration complète d'une appliance neuve depuis la seule copie externe (reconstruction après sinistre) n'est pas automatisée ; le temps de restauration n'a pas été mesuré sur de gros volumes.

## 0.8.0 — « Exploitation du cluster : quorum en direct, nœud perdu, reprise »
- **Quorum etcd en direct** (page Cluster) : root sonde chaque membre (état, santé, latence, index/terme raft, taille de la base, version) et publie voix saines / majorité requise / pannes tolérables ; la console se rafraîchit toutes les 5 s et demande à root une republication immédiate toutes les 15 s (opérateur et plus). Bandeaux : sain, sans marge, **perdu**, nœud connu de la configuration mais absent d'etcd.
- **Retrait d'un nœud perdu** (`ddibuntu-cluster remove-node NOM`, bouton « Retirer ») : efface le membre etcd, le registre, la clé de version et la clé de membre Patroni, écrit une marque de retrait que les autres nœuds appliquent (pairs, pare-feu), refuse : soi-même, nœud inconnu, quorum etcd absent, **primaire PostgreSQL en place**, retrait qui ferait perdre le quorum des nœuds restants. Répétable.
- **Reconstruction après perte du quorum** (`ddibuntu-cluster recover --yes`) : le nœud survivant relance etcd en `force-new-cluster` (indicateur retiré aussitôt après), sauvegarde le répertoire etcd (`ddibuntu.pre-recover.<date>`), oublie les nœuds perdus, redémarre Patroni. Refusée tant qu'etcd a son quorum ou qu'un autre nœud répond (deux cerveaux). **La réplication étant asynchrone, les dernières écritures non répliquées peuvent être perdues** (indiqué dans l'interface).

- **Console** : `POST /api/cluster/action` (admin ; `remove-node`, `take-ca`, `recover`) avec confirmation à retaper (nom du nœud, du nœud courant, du cluster) vérifiée par la console **et** par root, 409 explicites (`quorum_required`, `cannot_remove_self`, `no_escrow`, `quorum_present`…), une seule demande en attente (`action_pending`), audit ; `POST /api/cluster/refresh` (opérateur). Modales maison avec spinner, résultat de root relayé en notification.
- Frontière de privilèges : fichier `.cluster-action` ≤ 600 octets relu strictement par root (JSON, clés connues, noms valides, confirmation identique, lien symbolique refusé) ; message de retour issu de nos seuls messages, assaini.

## 0.7.0 — « Hygiène : adresses fantômes, RRL, tunnels DNS »
- **Adresses fantômes (IPAM › onglet « Fantômes »)** : adresses allouées (utilisée, réservation DHCP) que la découverte avait vues mais qui sont muettes depuis N jours (7 à 365). Les adresses jamais scannées, réservées, de passerelle ou d'infrastructure ne sont jamais listées. Libération en masse après confirmation (modale de la console) ; **le serveur revérifie le critère** au moment de supprimer : une adresse revue ou modifiée entre-temps est ignorée (409 `ghost_none_released` si rien n'est libérable), 500 adresses au plus par demande, action tracée dans le journal d'audit.
- **RRL — limitation de débit des réponses DNS** (DNS › Paramètres) : réponses par seconde, fenêtre, slip, clients exemptés (127.0.0.0/8 et ::1 par défaut). **Désactivé par défaut** ; « journaliser seulement » est activé par défaut pour observer avant de bloquer. Directive `rate-limit` sur une seule ligne, validée par `named-checkconf` et acceptée par la frontière de privilèges (`ddibuntu-reload`), donc répliquée telle quelle sur le secondaire.
- **Détection de tunnels / exfiltration DNS** (Filtrage › « Tunnels DNS ») : analyse du journal des requêtes par client et domaine (fenêtre 1 h à 7 jours) : nombre de sous-noms distincts, longueur moyenne, étiquette la plus longue, entropie des étiquettes longues, part de requêtes TXT/NULL/CNAME/MX/ANY → score et gravité (faible/moyenne/élevée ; seuls les scores ≥ 3 sont montrés) avec les indices détectés. Un domaine autorisé par une règle de filtrage est ignoré (moyen de faire taire un faux positif connu) ; « Bloquer » et « Autoriser » créent la règle après confirmation.
- API : `GET /api/ipam/ghosts?days=&subnet_id=`, `POST /api/ipam/ghosts/release`, `GET /api/filter/tunnel?hours=` ; réglages `rrl*` dans `GET/PUT /api/dns/settings`. Aucune migration.
- Tests : `unit-tunnel.test.ts` (6), `e2e-iter7.test.ts` (11 : bornes et persistance RRL, droits, critère des fantômes, libération refusée sur adresses récentes / jamais scannées / infrastructure, doublons d'identifiants, audit, tunnel détecté / client normal / domaine autorisé / fenêtre / injection), `unit-render.test.ts` (RRL validé par le vrai `named-checkconf`), `b12-bind-cluster.sh` (la directive traverse le rendu du cluster) ; interface vérifiée dans un navigateur automatisé.
- **Limites connues** : la détection est une heuristique (faux positifs possibles sur des services de télémétrie ou de réputation, faux négatifs sur un tunnel lent et discret) et ne repose que sur le journal des requêtes ; les adresses fantômes supposent des découvertes régulières (la découverte n'est pas encore planifiée) ; ni alerte automatique ni notification ; le RRL n'a pas été éprouvé sous charge réelle.

## 0.6.1 — « Le keytab Kerberos suit le cluster »
- **Réplication automatique de l'état Kerberos** (domaine, KDC, keytab) entre les nœuds de données : plus d'installation à refaire sur chaque nœud. Une installation, un changement ou un retrait fait depuis la console (sur le leader) est publié dans etcd, puis appliqué par l'autre nœud de données dans la minute (`ddibuntu-cluster follow`, ou aussitôt par la demande elle-même). Le nouveau primaire d'une bascule a donc déjà le keytab.
- **Le keytab n'est jamais lisible par l'arbitre** : la valeur stockée dans etcd est chiffrée (gpg AES-256, authentifié) avec une clé d'enveloppe dérivée (HMAC-SHA256, étiquette dédiée) de la clé de transfert de zone `ddi-xfr`, que seuls les nœuds de données possèdent. L'arbitre, qui héberge etcd, ne voit que du chiffré ; la phrase de passe ne passe jamais par une ligne de commande.
- **Règle de convergence** (`ddibuntu-cluster ad-sync`, verrou contre les exécutions simultanées) : état local = état d'etcd → rien ; état local modifié depuis la dernière synchronisation → on publie (la modification locale gagne) ; sinon on applique celui d'etcd ; premier contact d'un nœud → le cluster gagne s'il a un état. Un retrait est publié comme un état « none » et se propage de la même façon.
- **Rien d'appliqué à moitié** : `ddibuntu-ad import-state` valide tout (forme du JSON, domaine, KDC, keytab : principaux `DNS/…@DOMAINE`, chiffrements, taille) **avant** de modifier quoi que ce soit ; un état refusé laisse le nœud intact et n'est jamais republié à la place de l'état d'etcd. Une valeur illisible, altérée, annoncée avec une fausse empreinte, chiffrée avec une autre clé ou contenant un état invalide est refusée, signalée à la console, et se fait écraser par la première modification légitime.
- **Page « Active Directory »** : ligne « Cluster » (identique sur tous les nœuds / publié / reçu / en échec, avec le motif).
- Tests : `b14-ad.sh` (169 : export/import canoniques, refus sans effet, changement de domaine, réplication déclenchée par une demande, échec de réplication sans effet sur l'installation locale), **`b15-ad-cluster-live.sh` (80 : trois vrais etcd en TLS mutuel — publication chiffrée, arbitre aveugle, application, idempotence, modification, retrait, changement d'origine, premier contact, etcd injoignable, valeurs hostiles, reprise, exécutions simultanées, aucun secret résiduel)**, `e2e-iter4` (état de synchronisation relayé et assaini).
- **Limites connues** : une seule origine à la fois est supposée (seul le leader reçoit les écritures de la console) ; deux modifications simultanées sur deux nœuds isolés l'un de l'autre seraient départagées à la reconnexion par « le dernier à publier gagne ». Un nœud qui devient leader et applique un état reçu n'a pas de configuration BIND régénérée tant qu'un déploiement n'est pas fait depuis la console. Le même principal `DNS/…` sur les deux nœuds est à vérifier avec un vrai AD (SPN dupliqué ?). Non essayé avec un vrai Active Directory.

## 0.5.6 — itération 6 « Active Directory : Kerberos, GSS-TSIG, redirecteurs conditionnels »
- **Mises à jour DNS sécurisées (GSS-TSIG)** : BIND accepte les mises à jour authentifiées par Kerberos des machines du domaine (`update-policy` `ms-self` pour les comptes machine `PC1$` d'Active Directory, `krb5-self` pour les hôtes Kerberos `host/…`) ; chaque machine ne peut modifier **que son propre nom**. La clé DDNS de Kea reste acceptée dans la même zone (`grant ddi-ddns zonesub ANY`). Option par zone dans la console (« Mises à jour sécurisées »).
- **`ddibuntu-ad` (root)** : enregistre le domaine Kerberos (`/etc/ddibuntu-ad/ad.conf`, `/etc/krb5.conf` géré par l'appliance, l'original est conservé), installe le **keytab** du serveur DNS (`/etc/bind/krb5.keytab`, `root:bind 0640`, seul chemin que le profil AppArmor de `named` autorise) après contrôle (principaux `DNS/<nom>@DOMAINE` uniquement, domaine conforme, DES refusé, taille et format), publie un état sans secret (`/run/ddibuntu/ad-status.json`) et **teste** le keytab auprès du KDC (un ticket est obtenu puis détruit : joignabilité, heure, version de clé).
- **Frontière de privilèges** : la console ne peut ni déclarer `tkey-gssapi-keytab`/`tkey-*` (refusés par `ddibuntu-reload`), ni choisir le domaine : root **recompose** les `update-policy` à partir de son propre domaine, refuse tout octroi hors grammaire (`wildcard`, `krb5-subdomain`, types au-delà de A/AAAA, `deny`, `allow-update` ouvert, domaine différent) avant toute modification, puis ajoute lui-même `tkey-gssapi-keytab`. Le rendu de la console lit le domaine dans l'état publié par root, pas dans un réglage modifiable. Le keytab déposé par la console (fichier 0600) est supprimé par root après lecture, **même refusé**.
- **Cluster** : le secondaire ne retient aucune politique de mise à jour (grammaire seulement contrôlée) ; à la promotion, le nouveau primaire reçoit les politiques et `tkey-gssapi-keytab` s'il a le domaine et le keytab ; **sans configuration Kerberos sur ce nœud, les octrois Kerberos sont retirés et la promotion n'est jamais bloquée**.
- **Page « Active Directory »** (administrateurs/opérateurs) : domaine et contrôleurs, installation du keytab (modale personnalisée, secret jamais affiché ni renvoyé), test, retrait (confirmation personnalisée), indicateurs d'attente ; **assistant de redirecteurs conditionnels** : vérifie les contrôleurs (SOA, SRV LDAP/Kerberos) puis crée ou met à jour la zone de redirection (`ad_integrated`). Une zone locale de même nom est refusée (elle masquerait la redirection).
- **Règle découverte à l'essai** : BIND lit `PC1$@CORP.LOCAL` comme `pc1.corp.local` ; `ms-self` n'agit donc que dans la zone portant le nom du domaine. La console refuse `ms-self` ailleurs (`ms_self_zone_mismatch`) au lieu de laisser croire qu'il fonctionne.
- Migration 8 (`dns_zones.ddns_secure`), paquet `krb5-user` embarqué, unités `ddibuntu-ad-request.path/.service`.
- Tests : `b14-ad.sh` (130 : validation du domaine et du keytab, demandes hostiles de la console, recomposition par `ddibuntu-reload`, primaire / secondaire / promotion), `b14-ad-live.sh` (40 : **vrai KDC MIT**, **vrai `named`** configuré par `ddibuntu-reload` avec le keytab installé par `ddibuntu-ad`, vraies mises à jour `nsupdate -g` : nom propre accepté, noms d'autrui et du serveur refusés, `ms-self` et `krb5-self`, clé DDNS toujours acceptée, anonymes refusés, rotation de clé détectée, retrait qui coupe l'accès), tests unitaires (9) et de bout en bout (9) de la console.
- **Limites connues** : essayé avec un KDC MIT, **pas avec un Active Directory réel** (Windows/Samba) : formats de keytab `ktpass`, chiffrements AES/RC4 et comportement des clients Windows (négociation GSS-TSIG, mises à jour de PTR) sont à vérifier au premier laboratoire. L'envoi des enregistrements DHCP **vers** les contrôleurs AD en GSS-TSIG n'est pas fait (Kea 2.4 n'a pas le hook ; `nsupdate -g` depuis l'IPAM reste à écrire). Le keytab est installé **nœud par nœud** (il n'est pas répliqué) : chaque nœud de données doit le recevoir pour qu'après une bascule les clients Kerberos soient acceptés. `ms-self` ne couvre que A/AAAA (pas de PTR). Les mises à jour Kerberos reçues par BIND sont, comme tout DDNS, écrasées par le déploiement suivant des zones concernées (limite existante).

## 0.5.5 — itération 5 « Le cluster suit le leader »
- **Promotion de BIND** : quand Patroni change de leader, `ddibuntu-cluster follow` appelle `ddibuntu-reload --promote` sur le nouveau leader. Les zones reçues par transfert (binaires, avec leur journal IXFR) sont **converties en texte** (`named-compilezone -j`), contrôlées avant toute modification (une zone illisible fait refuser la promotion : le nœud reste secondaire et continue de servir), puis le nœud devient primaire BIND avec ses mises à jour dynamiques. Les zones jamais transférées restent vides avec un avertissement.
- **Ancien primaire** : il redevient secondaire et repart d'un **transfert complet** (ses fichiers de zone et journaux sont retirés), pour qu'une copie plus récente mais jamais transférée ne bloque pas le nouveau primaire. Le nouveau primaire fait foi (comme Patroni pour la base).
- **Console consciente de son rôle** : sur un secondaire, la base est en lecture seule ; la console répond 503 `replica` à toute écriture (avant d'écrire le moindre fichier), reste lisible avec la session ouverte sur le leader, ne lit plus le journal des requêtes, n'applique pas de migrations et attend celles du leader. Un secondaire promu reprend l'écriture sans redémarrage.
- **Page « Cluster »** (visible dès qu'un cluster existe) : nœuds, rôle de la base, rôle BIND, quorum, adresse de service, Kea HA, retard de réplication ; bascule contrôlée (modale de confirmation personnalisée, indicateur d'attente). La console ne fait que **déposer une demande** (un nom de nœud) ; `ddibuntu-cluster request` (root, déclenché par `ddibuntu-cluster-request.path`) la valide de nouveau (nœud de données existant, secondaire en bonne santé, pas le leader) et publie un résultat à message fixe.
- **État publié par root** (`/run/ddibuntu/cluster-status.json`, sans secret, chaque minute) lu par la console.
- **Mise à jour progressive** : `ddibuntu-cluster rolling-check` : le leader refuse la mise à jour tant qu'un secondaire en bonne santé n'est pas déjà à la version visée (la version de chaque nœud est partagée dans etcd) ; un secondaire mis à jour en premier reste sain (la santé annonce `waiting_leader`, pas de retour arrière) et attend les migrations du leader.
- Tests : `b12-bind-cluster.sh` (74), `b12-bind-cluster-live.sh` (deux vrais `named` : panne du primaire, promotion, DDNS conservé, retour de l'ancien primaire), `b10-cluster-live.sh` (changements de leader réels de Patroni pilotant BIND, demandes de bascule hostiles, **deux vraies consoles** : leader en écriture, secondaire en lecture seule, bascule demandée depuis la console), vitest (API cluster, état, droits, candidats).
- **Limites connues** : le journal des requêtes DNS d'un secondaire n'est pas ingéré tant qu'il n'est pas leader (le cockpit reflète le BIND du leader) ; la fenêtre entre la rétrogradation par Patroni et le prochain passage de `follow` (jusqu'à une minute) laisse l'ancien BIND primaire accepter des mises à jour dynamiques qui seront perdues ; les mises à jour DDNS non encore transférées au moment d'une panne sont perdues ; pas de coupure réseau réelle entre machines ; Keepalived et la promotion ne sont pas encore éprouvés ensemble sur un vrai commutateur.

## 0.5.4 — itération 4 « BIND primaire/secondaire, RPZ, Keepalived »
- **BIND secondaire dérivé par root** : `ddibuntu-reload` transforme la configuration répliquée de la console (`named.conf.options` / `named.conf.zones`, table `rendered_configs`) : zones primaires → zones **secondaires** (`primaries { PAIR key "ddi-xfr"; }`) sur le nœud qui suit (`--replica`), et sur le primaire `allow-transfer { key "ddi-xfr"; }`, `also-notify`, `transfer-source`/`notify-source` et `listen-on` sur l'adresse du réseau dédié. Lecture **fermée en cas de doute** : toute ligne inattendue de la console fait refuser le déploiement.
- **Transferts de zone signés** (AXFR/IXFR, TSIG `ddi-xfr` hmac-sha256) sur le réseau dédié uniquement ; le global `allow-transfer { none; }` de la console est conservé pour tout le reste. **La RPZ est une zone comme une autre** : elle est distribuée par le même mécanisme, sans copie de fichiers.
- **Clé TSIG du cluster** créée par le nœud autorité (aussi sur un cluster créé avant la 0.5.4, au premier `follow`), transmise dans le lot d'enrôlement (forme exacte vérifiée), `root:bind 0640`.
- **Keepalived (IP virtuelle)** : l'adresse virtuelle suit le **leader Patroni** (`vip-check` interroge `/primary` en TLS mutuel ; hors leader, l'instance passe en FAULT). Pas de leader → pas d'adresse virtuelle. VRRP en unicast sur le réseau dédié, VIP sur l'interface de service ; protocole 112 ouvert aux seuls pairs ; rien sur l'arbitre.
- `ddibuntu-cluster follow` gère aussi BIND (réplica : copie vérifiée par empreinte, la copie locale périmée des zones est supprimée pour ne jamais écraser la zone transférée ; primaire : rechargement complet).
- Tests : `b12-bind-cluster.sh` (transformation, cas hostiles), `b12-bind-cluster-live.sh` (deux vrais `named` : AXFR/IXFR signés, NOTIFY, DDNS → IXFR, RPZ distribuée, transferts non signés refusés), `b13-vip-live.sh` (vrai Keepalived dans des espaces de noms réseau), `b10-cluster-live.sh` étendu (clé TSIG propagée, `follow` en réplica et en primaire).
- **Limites connues** : la **promotion** du BIND secondaire et la console qui suit le primaire arrivent à l'itération 5 (aujourd'hui, le DNS reste servi par les deux nœuds mais les modifications se font sur le primaire) ; un secondaire déjà enrôlé avant la 0.5.4 doit être rattaché de nouveau pour recevoir la clé TSIG ; **constat antérieur à la 0.5.4** : `rndc reload` ne relit pas le fichier d'une zone dynamique (`allow-update`) — seul `freeze`/`thaw` le fait, au prix des noms dynamiques ; pas de coupure réseau réelle entre machines ; le test de panne de Keepalived reste simulé.

## 0.5.3 — itération 3 « Kea HA load-balancing »
- **Kea en haute disponibilité** (mode `load-balancing`, hooks `libdhcp_ha` + `libdhcp_lease_cmds`) dès qu'un cluster compte deux nœuds de données. Synchronisation des baux par un écouteur HTTP dédié de Kea (port 8000) en **TLS mutuel** avec les certificats du cluster, sur le réseau dédié.
- **Frontière de privilèges** : la console ne peut toujours pas déclarer de hook ; `ddibuntu-reload` (root) ajoute le bloc HA à partir de `cluster.conf`, exige les fichiers TLS, relit la configuration finale avec `kea-dhcp4 -t` et revient en arrière en cas d'échec. Rôles `primary`/`secondary` du hook déterminés par l'ordre des noms (identique sur les deux nœuds). Base de baux locale (fichier) en mode cluster ; le mot de passe de la base de baux n'est jamais copié.
- **Le secondaire suit la configuration** : migration 6 (`rendered_configs`, répliquée) alimentée à chaque déploiement ; `ddibuntu-cluster follow` (minuterie `ddibuntu-cluster-follow`, 1 min) vérifie l'empreinte, dépose le fichier et appelle `ddibuntu-reload --kea-only`. Sur le primaire, `follow` réapplique à l'arrivée du second nœud (le HA s'active sans nouveau déploiement).
- `ddibuntu-cluster status` : état HA de Kea (rôle, état local, état du partenaire, clients sans réponse) lu sur la socket de contrôle.
- Pare-feu : port 8000 ouvert aux seuls pairs du cluster. Utilisateur `_kea` ajouté au groupe `ddicluster` (lecture de la clé du nœud).
- Tests : `b11-kea-ha.sh` (injection, ordre des rôles, hostiles, retour arrière, vrai `kea-dhcp4 -t`) ; `b11-kea-ha-live.sh` (deux vrais Kea : load-balancing, TLS mutuel, 14 baux obtenus par de vrais échanges DHCP via un relais et retrouvés chez le partenaire, arrêt brutal du partenaire → `partner-down` → l'autre sert 10/10 nouveaux clients, retour → baux rattrapés) ; `b10-cluster-live.sh` étendu (`follow` sur un vrai Patroni : secondaire, primaire, empreinte altérée, hook injecté en base refusé).
- **Limites connues** : minuteries accélérées dans le test réel (production : 10 s / 60 s) ; pas de coupure réseau réelle entre machines ; les relais doivent lister les deux nœuds (le DHCP ne passe pas par la VIP) ; la console du secondaire ne suit pas encore le primaire (itération 5) ; DHCP en cluster = fichier de baux (les baux déjà en base PostgreSQL ne sont pas migrés).

## 0.5.2 — itération 2 « Fondations du cluster »
- **`ddibuntu-cluster`** (root) : `init`, `bundle`, `join`, `render`, `activate`, `status`, `switchover`. Un cluster = 2 nœuds de données (PostgreSQL conduit par **Patroni**) + 1 **arbitre** (etcd seul), sur le **réseau dédié**.
- **Quorum etcd (3 membres)** en TLS mutuel, écoute limitée à l'adresse du réseau dédié. Un nœud ajouté entre comme **learner** (sans voix) puis est promu votant une fois synchronisé : le quorum n'est jamais dégradé pendant l'enrôlement.
- **Autorité interne** (EC P-256) créée par `init` ; sa clé ne quitte jamais le premier nœud. Certificats de nœud (SAN = adresse du réseau dédié). La réplication PostgreSQL s'authentifie **par certificat client** (correspondance `pg_ident`), sans mot de passe de réplication ; l'API Patroni exige un certificat client.
- **Lot d'enrôlement chiffré** (OpenPGP AES-256, phrase de passe affichée une seule fois, empreintes SHA-256 vérifiées) : certificat et clé du nouveau nœud, configuration, et — pour un nœud de données — les secrets de la console qui doivent être identiques partout (`DDI_SECRET_KEY`…). Le contenu d'un lot est revalidé comme une entrée non fiable ; un lot ne peut pas créer d'autorité ; un nœud de données refuse de reprendre la base du cluster sans `--wipe-local-db`.
- Reprise d'une base existante : `init` adopte la base PostgreSQL de l'appliance (Patroni devient leader sur les données conservées).
- **Pare-feu** : nouvelle clé `CLUSTER_PEERS` ; 2379, 2380, 5432 et 8008 ne s'ouvrent qu'aux autres nœuds du cluster.
- **Console** : indicateur d'attente global (spinner + barre) sur toute écriture/déploiement/import/mise à jour dépassant 400 ms ; contrôle automatique qu'aucune boîte système (`confirm`/`alert`/`prompt`) n'est utilisée (les confirmations passent par la modale maison).
- Paquets embarqués : `patroni`, `etcd-server`, `etcd-client`, `python3-psycopg2`, `gnupg`, `openssl`, `curl`. etcd et Patroni restent **désactivés** tant que `ddibuntu-cluster` ne les active pas (le paquet etcd démarrerait sinon un magasin en clair).
- Tests : `b10-cluster.sh` (analyse stricte, lots hostiles, pare-feu) et `b10-cluster-live.sh` (3 nœuds simulés avec de vrais etcd/Patroni/PostgreSQL : enrôlement, réplication, bascule contrôlée, bascule automatique après arrêt brutal, réintégration, isolation sans quorum).
- **Registre des nœuds** dans etcd + minuterie `ddibuntu-cluster-sync` (chaque minute) : chaque nœud apprend les autres, met à jour Patroni et ouvre son pare-feu à leur adresse ; commande `sync`.
- Résultat des tests : `b10-cluster.sh` 73/73 ; `b10-cluster-live.sh` 81/81 (vrais etcd/Patroni/PostgreSQL sur 3 nœuds simulés). Console : build OK, 259 tests passent ; les 15 échecs restants sont ceux du banc sans `named`/`kea` (identiques à 0.5.1).
- **Limites connues** : pas encore de page « Cluster » dans la console (état via `ddibuntu-cluster status`) ; la console, BIND et Kea ne suivent pas encore le primaire (itérations 3 à 5) ; une installation existante doit recevoir les paquets ci-dessus (la mise à jour en ligne ne les installe pas) ; test de panne réelle sur machines non réalisé.

## 0.5.1 — itération 1 « Smart DDI »
- **Génération de configuration** : compteur monotone tenu par des déclencheurs en base (zones, enregistrements, étendues, pools, réservations DHCP, règles et listes de filtrage, réglages DNS/DHCP). Les numéros de série de zone et l'inventaire IPAM seul ne l'incrémentent pas. Chaque déploiement enregistre la génération rendue ; le tableau de bord affiche « déployée / à déployer » ; API `GET /api/system/config-generation`. Base de la détection d'écart entre nœuds du futur cluster.
- **Réservation DHCP pilotée par l'IPAM** : une adresse au statut « Réservation DHCP » avec MAC crée, met à jour ou retire sa réservation Kea dans la **même transaction** ; supprimer l'adresse supprime la réservation (clé étrangère en cascade) ; supprimer la réservation côté DHCP redonne le statut « utilisée ». Les réservations existantes sont rattachées à leur adresse par la migration. Retour explicite (`dhcp: created|updated|removed|no_mac|no_scope`).
- **Gabarits de réseau** : étendue DHCP créée avec le réseau (durée de bail, options DNS/domaine/NTP, routeur = passerelle), zone DNS des hôtes (A/AAAA + PTR automatiques à l'allocation, ou refusés explicitement avec `dns_zone_id: null`), règle de nommage par motif simple (`#` chiffre, `?` caractère, `*` suite) — volontairement pas d'expression régulière saisie (pas de ReDoS). Onglet « Gabarits » ; champ « Gabarit » sur les réseaux.
- **Santé honnête** : `/api/health` répond 503 tant que les migrations ne sont pas terminées (la vérification de santé de la mise à jour en ligne et les tests ne peuvent plus conclure trop tôt).
- Document d'architecture du cluster validé : `docs/ARCHITECTURE-CLUSTER.md`.

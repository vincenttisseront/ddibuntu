# Architecture du mode cluster

Statut : **réalisée** (0.22.0). Ce document décrit ce que le code fait aujourd'hui ; chaque affirmation renvoie à `ddibuntu-cluster` (script root, `src/rootfs/usr/local/sbin/`), à `ddibuntu-reload` (BIND et Kea) ou à la console (`webui/server/utils/cluster.ts`). Les points que le code ne démontre pas, ou qu'aucun essai en conditions réelles n'a confirmés, sont rassemblés dans « Limites et points non éprouvés ». Le détail de chaque itération (choix de conception, tests) est conservé en annexe.

## En bref
- Un cluster est un ensemble de **nœuds de données** (rôle `data`) auxquels s'ajoute, si on le souhaite, **un arbitre** (rôle `witness`).
- **Tous les nœuds de données portent les données** : etcd, Patroni, PostgreSQL (une copie répliquée de la base), la console, BIND, Kea, FreeRADIUS et la PKI (EJBCA) sont installés sur chacun. Un seul nœud de données est **leader** à un instant donné.
- **Le leader PostgreSQL (Patroni) décide de tout** : c'est lui qui sert les écritures de la console, qui est BIND primaire, qui porte l'adresse virtuelle, qui exécute RADIUS et la PKI. Les autres nœuds de données suivent.
- **Le quorum est celui d'etcd** (majorité des membres). Il n'y a pas de « nœud de quorum » obligatoire : l'arbitre est un membre etcd de plus, sans données, qui sert à garder une majorité quand un nœud de données tombe. Un cluster sans arbitre fonctionne, mais **sans tolérance de panne** quand il n'a que deux nœuds de données (voir le tableau plus bas).
- Le DNS et le DHCP **ne dépendent pas du leader** : chaque nœud de données répond aux clients (BIND primaire/secondaire, Kea en haute disponibilité).

## Décisions validées
| # | Décision | Choix |
|---|---|---|
| 1 | Bascule | **Automatique** (Patroni), fondée sur le quorum etcd ; un arbitre facultatif sert à tolérer la perte d'un nœud de données |
| 2 | Ordre des travaux | Cluster **avant** l'interopérabilité AD |
| 3 | Réseau | Un **réseau dédié** à la réplication, au quorum, à la haute disponibilité de Kea et à VRRP (séparé du réseau de service) |
| 4 | Essais | Chaque fonction est testée avec de vrais démons (etcd, Patroni, PostgreSQL, Kea) sur boucle locale ; les coupures réseau réelles entre machines ne sont pas démontrées |

## Rôles de nœud
| | Nœud `data` | Nœud `witness` (arbitre) |
|---|---|---|
| etcd (membre votant) | oui | oui |
| Patroni et PostgreSQL | oui | non |
| BIND, Kea, FreeRADIUS, EJBCA | oui (selon le rôle Patroni) | non |
| Console | oui (écriture sur le leader, lecture ailleurs) | sans base de données : aucune utilité ; l'état de ce service n'a pas été vérifié |
| Keepalived et adresse virtuelle | oui, si une adresse virtuelle est définie | non |
| Minuteries `follow` et demandes d'administration | oui | non (synchronisation seulement) |
| Clé TSIG, secrets de la console, clé de l'autorité | reçoit | ne reçoit **rien** : il ne peut pas déchiffrer ce qu'etcd contient |
| Sauvegardes, paquets embarqués (podman, FreeRADIUS) | oui | non |

- Le rôle se choisit à la création du lot d'enrôlement (`ddibuntu-cluster bundle --role data|witness`) ; la console crée un nœud de données seulement pour le **premier** nœud (`init`) et propose les deux rôles pour les suivants.
- Le code ne limite pas le nombre de nœuds, mais la console en affiche **16 au plus**. **Kea HA et le BIND secondaire exigent exactement deux nœuds de données** (`ddibuntu-reload` : `len(data) != 2`) ; Keepalived n'a qu'**un** pair VRRP (le dernier nœud de données qui n'est pas soi).

## Quorum et tailles de cluster
- **Membres etcd** : tous les nœuds, arbitre compris. TLS mutuel obligatoire (ports 2379 client, 2380 pairs). Un nouveau nœud entre comme **« learner »** (sans voix), puis est promu : le quorum n'est pas dégradé pendant l'enrôlement.
- **Règle** : votants = membres non « learner » connus d'etcd ; majorité requise = ⌊votants / 2⌋ + 1 ; tolérance = membres sains − majorité (`quorum_json`, publié dans l'état du cluster).

| Composition | Votants | Majorité | Pannes tolérées | Ce qui se passe quand un nœud tombe |
|---|---|---|---|---|
| 1 nœud de données | 1 | 1 | 0 | pas de réplique : le service s'arrête avec le nœud |
| **2 nœuds de données, sans arbitre** | 2 | 2 | **0** | le quorum etcd est perdu : le nœud restant n'est plus utilisable en écriture (un leader sans quorum se rétrograde, sa VIP disparaît). DNS et DHCP continuent de répondre. Reprise par `ddibuntu-cluster recover`. L'alerte « marge de quorum nulle » le signale. |
| **2 nœuds de données + 1 arbitre** | 3 | 2 | 1 | configuration de référence : bascule automatique sans intervention (validée avec de vrais etcd et Patroni) |
| 3 nœuds de données ou plus | 3 et + | 2 et + | 1 et + | etcd et Patroni le permettent, mais Kea HA et le BIND secondaire ne sont pas pris en charge au-delà de deux nœuds de données (voir ci-dessus) : non éprouvé |

- **Nœud isolé** : sans quorum, le leader perd son verrou dans etcd (comportement de Patroni : `ttl` 30 s, `loop_wait` 10 s, `retry_timeout` 10 s) ; PostgreSQL redevient lecteur, la console refuse toute écriture par un `503 replica` avant tout effet de bord, les tâches de fond qui écrivent s'arrêtent, `vip-check` retire l'adresse virtuelle.
- **Opérations qui exigent le quorum** (refusées sinon, `409 quorum_required`) : test de bascule, retrait d'un nœud, adresse virtuelle, réseau dédié, mise à jour progressive, nœud préféré, lot d'enrôlement. `change-ip` exige en plus une **marge** (un nœud de plus que la majorité). À l'inverse, `recover` n'est autorisé que **sans** quorum et si aucun autre nœud ne répond.

## Topologie de référence (2 nœuds de données + arbitre)
```
        clients DNS · relais DHCP · administrateurs
                        │  réseau de service
        VIP de service (Keepalived, suit le LEADER PostgreSQL)
           │                                │
 ┌─────────┴──────────┐          ┌──────────┴─────────┐        ┌────────────────┐
 │ Nœud 1 — LEADER    │          │ Nœud 2 — SECONDAIRE│        │ Nœud 3 ARBITRE │
 │ Console (écriture) │          │ Console (lecture)  │        │ (facultatif)   │
 │ PostgreSQL primaire├─ WAL ───►│ PostgreSQL réplique│        │ etcd seulement │
 │ BIND primaire      ├─ AXFR ──►│ BIND secondaire    │        │ pas de données │
 │ FreeRADIUS, EJBCA  │          │ (arrêtés)          │        │ ni de secrets  │
 │ Kea ◄── HA load-balancing ──► │ Kea                │        │                │
 │ etcd · Patroni     │          │ etcd · Patroni     │        │                │
 └─────────┬──────────┘          └──────────┬─────────┘        └───────┬────────┘
           └─────── réseau dédié : réplication, HA Kea, etcd, VRRP ────┘
```
Sans arbitre, le nœud 3 disparaît : le cluster reste à deux nœuds de données et deux votants etcd (tolérance nulle).

## Principes
- **Source de vérité** : PostgreSQL. Le leader est le seul à écrire ; chaque rôle (console en écriture, BIND primaire, VIP, RADIUS, PKI) suit ce leader. `ddibuntu-cluster follow` (minuterie d'une minute) lit le rôle Patroni local et aligne le reste ; Keepalived déplace la VIP sans attendre.
- **Baux DHCP** : pas dans la base répliquée. Chaque Kea garde ses baux dans un fichier local ; le hook HA (`libdhcp_ha`, mode `load-balancing`, avec `libdhcp_lease_cmds`) les synchronise sur le réseau dédié (port 8000, TLS mutuel). Les rôles HA (`primary` / `secondary`) viennent de l'ordre alphabétique des noms de nœuds, **indépendamment** du leader PostgreSQL. Les relais DHCP doivent lister **les deux adresses réelles** des nœuds : le DHCP ne passe pas par la VIP.
- **DNS** : le leader est BIND primaire (zones, DDNS, RPZ). L'autre nœud est secondaire (AXFR/IXFR signé TSIG sur le réseau dédié, NOTIFY) ; les deux répondent aux clients. À la bascule, le secondaire est promu.
- **Configuration identique** : la console enregistre dans la table répliquée `rendered_configs` la configuration Kea et BIND avec son empreinte SHA-256 ; le nœud suiveur la relit, vérifie l'empreinte et la déploie. La console ne déclare jamais de hook Kea : `ddibuntu-reload` (root) refuse tout `hooks-libraries` venant de la console et ajoute lui-même le bloc HA.
- **Console** : sur un secondaire, lecture seule (`503 replica` pour toute écriture) ; la connexion y est possible par un jeton signé (4 h au plus, sans révocation individuelle) ; un compte d'annuaire doit s'être connecté une première fois sur le leader.
- **Adresse virtuelle** : Keepalived (VRRP unicast sur le réseau dédié). Le script `vip-check` interroge l'API Patroni `/primary` en TLS mutuel : seul le leader garde l'adresse ; sans leader, personne ne la porte.

## Création, jonction, retrait
- **`init`** (premier nœud) : crée l'autorité interne (EC P-256, 3650 jours, la clé ne quitte jamais ce nœud), le certificat du nœud, la clé TSIG `ddi-xfr`, la configuration, puis active etcd et (nœud de données) Patroni. Le réseau dédié est celui de l'interface qui porte l'adresse du nœud, ou le `--net` fourni.
- **`bundle`** (sur le nœud qui porte l'autorité) : ajoute le nouveau membre à etcd en « learner » et produit un **lot chiffré** (GPG symétrique, phrase de passe affichée une seule fois) contenant la configuration, le certificat et la clé du nouveau nœud, la CA et, pour un nœud de données, la clé TSIG et les secrets de la console. Il n'y a **pas de jeton à usage unique** : c'est un fichier chiffré ; les lots non retirés sont détruits au bout d'une heure.
- **`join`** (nouveau nœud) : déchiffre, vérifie le manifeste SHA-256 et **revalide** tout comme une entrée non fiable ; sur un nœud de données, **efface la base locale** (`--wipe-local-db` obligatoire, implicite depuis la console) et la recrée par réplication depuis le leader.
- **Retrait** : pas de `leave`. `remove-node` s'exécute depuis un **autre** nœud : refusé pour soi-même, pour le leader en place, ou si les nœuds restants perdraient le quorum. `recover` reconstruit etcd à un membre après la perte du quorum. `take-ca` reprend l'autorité sur un nœud de données quand son porteur est injoignable (clé publiée chiffrée dans etcd).
- **Synchronisation** (`sync`, minuterie d'une minute) : relit le registre des nœuds dans etcd, ajoute ou retire les pairs, recalcule Patroni, Keepalived et le pare-feu, applique les réglages communs.

## Base de données (Patroni)
- Réplication **asynchrone** (`synchronous_mode: false`) : une bascule peut perdre les transactions les plus récentes, dans la limite du retard (`maximum_lag_on_failover` : 1 Mio). `pg_rewind` et les slots de réplication sont actifs ; chaque nœud de données peut devenir leader (`nofailover: false`).
- Réplication et `pg_rewind` en `sslmode: verify-full` avec authentification **par certificat** (pas de mot de passe de réplication) ; TLS 1.2 au moins. L'API REST de Patroni exige un certificat client.
- **Bascule contrôlée** : `ddibuntu-cluster switchover` (`patronictl switchover`) ; depuis la console, un administrateur choisit un candidat (secondaire de données en bonne santé, ni leader ni arbitre) ; root revalide.
- **Nœud préféré** : simple consigne publiée dans etcd ; la console signale l'écart avec le leader et propose la bascule contrôlée, jamais de retour automatique.
- **Test de bascule** (`drill`) : vraie bascule mesurée (fenêtre sans primaire, promotion, rétrogradation, réintégration), retour au primaire d'origine facultatif, rapport conservé dans etcd (20 derniers). Exige au moins deux nœuds de données.

## Ce qui suit le leader
| Service | Leader | Secondaire de données |
|---|---|---|
| Console | écriture | lecture seule (`503 replica`) |
| BIND | primaire (zones, DDNS, RPZ) | secondaire, zones transférées en AXFR/IXFR (clé TSIG) |
| Kea | HA load-balancing | HA load-balancing (les deux servent les clients) |
| Adresse virtuelle | portée | retirée |
| FreeRADIUS | actif (la console du nouveau leader rejoue le dernier déploiement, 1 à 2 minutes) | arrêté et désactivé |
| PKI (EJBCA) | actif (état synchronisé par etcd ; reprise 2 à 3 minutes, pas d'actif-actif) | en veille, image déjà tirée |
| Keytab Kerberos / domaine | applique | reçoit par etcd, chiffré (clé dérivée de `ddi-xfr`) |

## Ports et pare-feu
Le pare-feu (`nftables`) n'ouvre aux **seuls pairs** du cluster que : TCP 2379 et 2380 (etcd), 5432 (PostgreSQL), 8000 (Kea HA), 8008 (API Patroni) et le protocole IP 112 (VRRP). Le DNS (53) et le DHCP (67) sont ouverts à tous par défaut ; RADIUS et la PKI le sont selon leurs réseaux autorisés. Ces règles sont les mêmes sur un arbitre.

## Certificats et secrets
- Certificats de nœud : 825 jours, renouvelés automatiquement à 60 jours de l'échéance ; la clé privée ne quitte jamais le nœud (il crée une demande, **seul le nœud porteur de l'autorité signe**). Le certificat de l'autorité **n'est pas renouvelé automatiquement** (affiché, alerte d'échéance).
- Secrets partagés (keytab, état de la PKI, clé de l'autorité, sauvegardes) : chiffrés avant d'être publiés dans etcd, avec une clé dérivée de `ddi-xfr` que seuls les nœuds de données possèdent.

## Opérations
- **Mise à jour progressive** : un ordre commun dans etcd (quorum et tous les nœuds sains exigés) ; chaque nœud s'applique à son tour : **arbitre, puis secondaires, puis le leader en dernier, sur place** (il n'y a pas de bascule automatique avant la mise à jour du leader). Un échec suspend la file. Un nœud qui n'a pas la version attendue reste « en attente » ; un secondaire dont le schéma est en retard répond `503 schema_pending` jusqu'aux migrations du leader.
- **Sauvegardes** : prises sur le leader seulement ; archivage WAL sur chaque nœud de données ; réglages communs dans etcd ; restauration à un instant donné depuis le leader (Patroni en pause, base remplacée **sans changer de leader**, puis reconstruction des secondaires).
- **Réglages communs** : adresse virtuelle, VRID, réseau dédié (`set-vip`, `clear-vip`, `set-net`) publiés une fois dans etcd avec une révision croissante ; chaque nœud les applique à sa synchronisation. `change-ip` déplace l'adresse d'un nœud avec l'accord des autres (pare-feu ouvert à la nouvelle adresse avant le changement), refusé sur le leader.
- **Frontière de privilèges** : la console écrit des demandes (≤ 1 Kio, jeu de clés exact) dans un dossier dédié ; root les revalide, exige la confirmation par retapage du nom (cluster ou nœud), exécute et publie un résultat à message fixe. Une demande à la fois.

## Supervision
- `ddibuntu-health` (une fois par minute) photographie services, PostgreSQL, disques, certificats, heure, charge ; chaque nœud, arbitre compris, publie sa santé dans etcd (une clé par nœud).
- Le moteur d'alertes ne tourne que sur la console **accessible en écriture** (le leader). Règles de cluster : état périmé, quorum perdu, marge de quorum nulle, membre hors service (avertissement pour l'arbitre), absence de leader, etcd malsain, retard ou défaut de réplique, changement de leader, adresse virtuelle non portée, nœud revenu, resynchronisation, retour au nœud préféré possible.
- Prometheus : métriques `ddibuntu_cluster_*` et `ddibuntu_node_*` ; chaque console expose sa propre vue (à interroger sur la VIP pour suivre le leader). Il n'y a pas de métrique pour Kea HA, la mise à jour ni le test de bascule.
- **Page « Cluster »** (console) : état du nœud (rôle PostgreSQL, rôle BIND, quorum, VIP), Kea HA, mise à jour, opérations et reprise, test de bascule, réglages (VIP, réseau, certificats, adresse d'un nœud, nœud préféré), tableau des nœuds. Lecture pour tout utilisateur, actions pour les administrateurs, depuis un nœud de données seulement.

## Limites et points non éprouvés
- **Deux nœuds de données sans arbitre : aucune tolérance de panne** (la perte d'un nœud fait perdre le quorum etcd). Pour tolérer une panne il faut un arbitre ou un troisième membre etcd.
- **Plus de deux nœuds de données** : Kea HA et le BIND secondaire ne sont pas pris en charge (`ddibuntu-reload` exige exactement deux nœuds de données, et `follow` échoue sur le chemin secondaire) ; Keepalived n'a qu'un pair. Non éprouvé.
- **L'arbitre** : le code lui donne seulement etcd et la synchronisation ; ni Patroni, ni base de données, ni Keepalived, ni PKI, ni RADIUS. La minuterie `follow` n'est activée que sur les nœuds de données : la publication de la version d'un arbitre pour la mise à jour progressive passe par `ddibuntu-selfupdate`. Le comportement d'un arbitre réel n'a pas été vérifié.
- **Pas d'actif-actif** : une seule PKI (interruption de 2 à 3 minutes à chaque bascule) et un seul FreeRADIUS (1 à 2 minutes). Les journaux d'authentification RADIUS sont propres à chaque nœud.
- **Réplication asynchrone** : perte possible des dernières transactions à la bascule, dans la limite du retard autorisé.
- Le certificat de l'autorité n'est pas renouvelé automatiquement ; un jeton de session de secondaire ne se révoque pas individuellement avant 4 h.
- **Non démontré en conditions réelles** : coupure réseau entre machines, VRRP sur un vrai commutateur, bascule réelle de la PKI et de RADIUS, comportement d'un arbitre, minuteries de production de Kea HA, charge.

## Écarts assumés par rapport au cahier des charges
1. **Atomicité** : aucune transaction ne couvre PostgreSQL et deux démons. Garantie réelle : écriture atomique en base (IPAM + DNS + réservation DHCP dans une transaction) ; application convergente avec **génération de configuration**, validation avant déploiement, retour arrière, détection d'écart entre nœuds.
2. **GSS-TSIG** : le hook GSS-TSIG de Kea n'existe pas dans Kea 2.4 (Ubuntu 24.04), vérifié (`libdhcp_*` du paquet : ni `gss_tsig`). Repli retenu à l'itération 6 : BIND authentifie lui-même les clients du domaine (`update-policy` `ms-self` / `krb5-self`). L'envoi des enregistrements de l'appliance vers les contrôleurs AD par `nsupdate -g` reste à écrire.
3. **Test de panne** : sans laboratoire, la bascule réelle n'est pas démontrée ; chaque itération livre ses procédures de test pour le premier labo.

## Itération 3 — Kea HA : comment c'est réalisé
- **La console ne déclare jamais de hook.** Le bloc `hooks-libraries` donne l'exécution de code à Kea (root) : `ddibuntu-reload` (root) refuse tout `hooks-libraries` venant de la console et **ajoute lui-même** le bloc HA à partir de `/etc/ddibuntu-cluster/cluster.conf` (fichier root). Il le fait seulement sur un nœud de **données** quand **deux** nœuds de données existent ; un arbitre ou un nœud seul reste en Kea simple. Les bibliothèques sont cherchées dans les dossiers de Kea (jamais un chemin venu d'ailleurs), les certificats doivent exister, et la configuration **finale** est relue par `kea-dhcp4 -t` avant tout rechargement ; échec → retour arrière.
- **Rôles déterministes** : les deux nœuds de données sont triés par nom ; le premier est `primary` du hook, le second `secondary`. Même résultat sur les deux nœuds quel que soit l'ordre de `PEERS`. Ce rôle HA n'a rien à voir avec le primaire PostgreSQL : un nœud qui perd la base reste un serveur DHCP à part entière.
- **Baux** : en mode cluster, base de baux = fichier local (`/var/lib/kea/kea-leases4.csv`), synchronisé par le hook. La base PostgreSQL de baux n'est pas utilisée (elle est en lecture seule sur le secondaire). Le mot de passe de la base de baux n'est jamais copié dans la configuration partagée.
- **Même configuration sur les deux nœuds** : à chaque déploiement, la console enregistre la configuration Kea (sans mot de passe) dans la table répliquée `rendered_configs` avec sa génération et son empreinte SHA-256. Sur le **secondaire**, `ddibuntu-cluster follow` (minuterie d'une minute) lit cette ligne dans sa copie locale de la base, vérifie l'empreinte, dépose le fichier et appelle `ddibuntu-reload --kea-only` (mêmes contrôles qu'en local ; une base compromise ne peut donc pas faire charger un hook). Sur le **primaire**, `follow` réapplique quand la liste des nœuds de données change (arrivée du second nœud) : le HA s'active sans nouveau déploiement.
- **Pare-feu** : le port 8000 n'est ouvert qu'aux pairs du cluster (`CLUSTER_PEERS`). Les relais DHCP doivent lister **les deux adresses réelles** des nœuds de données.
- **Délais de production** : `heartbeat-delay` 10 s, `max-response-delay` 60 s, `max-ack-delay` 5 s, `max-unacked-clients` 5. Le serveur restant ne prend les clients du partenaire qu'après avoir constaté des clients sans réponse (champ `secs` > `max-ack-delay`) : sans trafic client, l'état reste `communication-recovery`.
- **À vérifier au premier laboratoire** : coupure réseau réelle entre deux machines, minuteries de production, relais réels, charge.

## Itération 4 — BIND et adresse virtuelle : comment c'est réalisé
- **La console ne connaît pas le cluster.** Elle écrit une configuration BIND ordinaire (`allow-transfer { none; }` global). `ddibuntu-reload` (root) lit `named.conf.options` et `named.conf.zones` de façon **stricte** (formats exacts produits par `render.ts`) et refuse toute ligne inattendue : une base compromise ne peut pas ouvrir un transfert ni charger une clé.
- **Secondaire dérivé, jamais copié** : sur le nœud qui suit (`--replica`), chaque zone primaire devient une zone `secondary` dont le `primaries` est le pair du réseau dédié, signé par la clé `ddi-xfr`. Les fichiers de zone ne sont **pas** copiés : BIND les transfère (AXFR, puis IXFR après chaque mise à jour, y compris le DDNS). La copie locale périmée du dossier généré est supprimée à chaque passage.
- **Primaire** : `allow-transfer { key "ddi-xfr"; }` (en plus d'une ACL propre à la zone), `also-notify` vers le pair, `notify-source`/`transfer-source`/`listen-on` sur l'adresse du réseau dédié, `server PAIR { keys "ddi-xfr"; }`.
- **RPZ** : zone ordinaire transférée ; le secondaire applique donc les mêmes listes que le primaire sans mécanisme particulier.
- **Clé TSIG** : créée par le nœud autorité (`init`, ou premier `follow` d'un cluster plus ancien), embarquée dans le lot d'enrôlement, validée sur sa forme exacte avant installation (`root:bind 0640`).
- **IP virtuelle** : Keepalived (VRRP unicast sur le réseau dédié). Le script `vip-check` interroge l'API Patroni `/primary` en TLS mutuel : seul le leader PostgreSQL garde l'adresse. Sans leader, personne ne la porte (mieux vaut ne pas répondre que répondre depuis une base en lecture seule). Aucun Keepalived sur l'arbitre ; protocole 112 ouvert aux seuls pairs.
- **Réalisé à l'itération 5** (voir plus bas) : promotion du BIND secondaire, console et Kea qui suivent le primaire, page « Cluster ».
- **À vérifier au premier laboratoire** : coupure réseau réelle, comportement de VRRP sur un vrai commutateur, charge des transferts, zones dynamiques (`rndc reload` ne les relit pas).

## Itération 5 — suivre le leader : comment c'est réalisé
- **Une seule source de vérité : Patroni.** Le leader de la base est aussi le nœud qui sert les écritures de la console, le BIND primaire et la VIP. `ddibuntu-cluster follow` (1 min) lit le rôle Patroni local et aligne le reste ; Keepalived déplace la VIP sans attendre (il interroge Patroni toutes les quelques secondes).
- **Promotion BIND (`ddibuntu-reload --promote`)** : la configuration `named.conf.*` répliquée est retransformée en primaire (même code que le déploiement). Les fichiers de zone, eux, sont ceux que le nœud a reçus par transfert : BIND les stocke en binaire avec un journal, `named-compilezone -j -f raw -F text` les convertit en texte avec le journal appliqué (les noms créés par DDNS avant la panne sont conservés), le journal devenu incohérent est supprimé. Tout est contrôlé **avant** la première modification ; un échec laisse le nœud secondaire.
- **Retour d'un ancien primaire** : `--replica` après un rôle `primary` supprime ses fichiers de zone et journaux : un transfert complet depuis le nouveau primaire remplace tout (une copie « plus récente » ne serait jamais écrasée, BIND la jugeant à jour).
- **Console** : `pg_is_in_recovery()` décide. Secondaire = lecture seule : les requêtes qui écrivent sont refusées par un 503 `replica` **avant** tout effet de bord (déploiement de fichiers compris), les sessions (répliquées) restent lisibles, aucune migration n'est tentée (elles viennent du leader), les tâches de fond qui écrivent sont suspendues. Promu, le nœud reprend l'écriture en quelques secondes.
- **Demande de bascule** : la console dépose un fichier d'une ligne (nom de nœud) dans le seul dossier qui lui est ouvert en écriture ; root le relit comme un simple nom, le vérifie contre `cluster.conf` et l'état réel de Patroni (candidat = secondaire de données en bonne santé, pas le leader), exécute `patronictl switchover` et publie un résultat à message fixe.
- **Mise à jour progressive** : chaque nœud publie sa version dans etcd. Le leader n'accepte la mise à jour en ligne que lorsque les secondaires sains sont déjà à la version visée : on met à jour les arbitres, puis les secondaires, puis le leader en dernier, sur place (la file de l'itération 16 ne bascule pas automatiquement). Un secondaire sur le nouveau logiciel mais l'ancien schéma annonce `waiting_leader` (l'installation n'est pas annulée), répond `schema_pending` et attend les migrations du leader. **Paquets (0.14.11)** : chaque nœud de données pose podman et FreeRADIUS (livrés dans l'archive) pendant son propre tour de la mise à jour, sans accès à Internet ; l'arbitre n'en reçoit aucun. Pour le passage depuis une version qui ne posait aucun paquet, `ddibuntu-cluster follow` (`pkg_step`) lance en arrière-plan `ddibuntu-selfupdate packages --auto` si un paquet de `update-packages` manque (un essai toutes les 6 h au plus).
- **Isolation** (déjà éprouvée à l'itération 2 pour la base) : un leader sans quorum devient inutilisable en écriture ; sa VIP disparaît (vip-check) ; DNS et DHCP continuent de répondre (Kea HA, BIND secondaire).
- **À vérifier au premier laboratoire** : coupure réseau réelle, durée de la fenêtre de rétrogradation (≤ 1 min), bascule sous charge DHCP, grandes zones.

## Itération 6 — Active Directory : comment c'est réalisé
- **Deux rôles distincts.** (1) *Recevoir* : BIND de l'appliance accepte les mises à jour GSS-TSIG des machines du domaine. (2) *Résoudre* : les requêtes du domaine AD sont renvoyées à ses contrôleurs par des redirecteurs conditionnels (zone `forward only`, `ad_integrated`). L'*envoi* des baux vers les contrôleurs AD en GSS-TSIG n'est pas fait.
- **Qui détient quoi.** Le domaine Kerberos et le keytab appartiennent à **root** (`ddibuntu-ad` : `/etc/ddibuntu-ad/ad.conf`, `/etc/bind/krb5.keytab`). La console propose des octrois `update-policy` par zone ; `ddibuntu-reload` les **relit et les recompose** à partir du domaine de root (jamais celui de la console), refuse tout ce qui sort de la grammaire (trois formes seulement : `grant ddi-ddns zonesub ANY`, `grant REALM ms-self . A AAAA`, `grant REALM krb5-self . A AAAA`) et ajoute `tkey-gssapi-keytab`. `tkey-*` est une directive interdite venant de la console. Le rendu de la console lit le domaine dans `/run/ddibuntu/ad-status.json` (publié par root) : il ne peut pas diverger de ce que root acceptera.
- **Demandes de la console.** Même schéma que la bascule : `.ad-request` (JSON ≤ 4 Kio) + `.ad-keytab` (0600, secret) déposés dans le seul dossier ouvert à la console ; l'unité `ddibuntu-ad-request.path` lance `ddibuntu-ad request`, qui revalide tout, **supprime le keytab déposé même refusé**, relance `ddibuntu-reload` (sauf sur un secondaire) et publie `ad-result.json`. Une demande à la fois (409 `request_pending`). Le secret passe brièvement par le processus de la console (comme un mot de passe saisi dans un formulaire) ; la voie en ligne de commande (`ddibuntu-ad install-keytab`) l'évite.
- **Politiques et cluster.** Un secondaire ne retient aucun octroi (il n'accepte pas de mises à jour). À la promotion, le nouveau primaire applique les politiques avec **son propre** domaine et **son propre** keytab ; s'il n'en a pas, il retire les octrois Kerberos (avec avertissement) plutôt que de refuser la promotion : un défaut de configuration AD ne doit jamais empêcher une bascule. Depuis la 0.6.1, le keytab **est répliqué** entre les nœuds de données (voir « Itération 7 ») : on l'installe une fois, sur le leader ; son principal doit être `DNS/<nom que les clients résolvent>` (le nom de l'adresse de service).
- **Règles apprises à l'essai (KDC MIT, `named` 9.18).** `ms-self` lit `PC1$@CORP.LOCAL` comme le nom `pc1.corp.local` : il n'agit que dans la zone portant le nom du domaine ; `krb5-self` compare l'instance du principal (`host/pc1.corp.local`) au nom mis à jour. `update-policy` exclut `allow-update` : la clé DDNS de Kea devient donc un octroi de la politique. Le keytab doit se trouver dans `/etc/bind/` (profil AppArmor de `named`). `klist` marque RC4 « DEPRECATED » : accepté (anciens domaines), DES/3DES refusés.
- **À vérifier au premier laboratoire avec un vrai AD** : keytab produit par `ktpass` (type de chiffrement, `-mapuser`), négociation GSS-TSIG des clients Windows, mises à jour de PTR, interaction avec les zones intégrées à l'AD, cluster avec le même principal sur les deux nœuds (SPN dupliqué dans l'AD ?).

## Itération 7 — le keytab suit le cluster : comment c'est réalisé
- **Où vit l'état.** Dans etcd, clé `/ddibuntu-cluster/ad/state`, sous la forme `{"v":1,"sha":"<sha256 de l'état>","blob":"<état chiffré, base64>"}`. L'état clair est le JSON canonique `{"kdcs":[…],"keytab":"<base64>","realm":"…"}` produit par `ddibuntu-ad export-state` (`{}` = rien de configuré ; le retrait est publié avec `sha":"none"`).
- **Confidentialité.** Chiffrement symétrique gpg (AES-256, MDC) ; la phrase de passe est dérivée par HMAC-SHA256 de la clé de transfert de zone `ddi-xfr` avec l'étiquette `ddibuntu-ad-keytab-v1`. Seuls les nœuds de données ont cette clé : l'**arbitre, qui héberge etcd, ne peut rien déchiffrer**. etcd n'est joignable qu'en TLS mutuel. La phrase de passe transite par l'environnement et un descripteur de fichier, jamais par une ligne de commande ; les fichiers temporaires (dossier 0700) sont effacés (`shred`) à la sortie.
- **Qui applique quoi.** `ddibuntu-cluster ad-sync` (appelé au début de chaque `follow`, donc chaque minute, et par `ddibuntu-ad request` après toute modification) compare l'état local (L), celui d'etcd (E) et le dernier synchronisé (S, fichier local) : L = E → rien ; L ≠ S → publication ; sinon application de E ; S inconnu → E gagne s'il existe, sinon publication. Verrou `flock` contre les exécutions simultanées.
- **Application sûre.** `ddibuntu-ad import-state` lit strictement l'entrée, valide le domaine, les KDC et le keytab (mêmes contrôles que l'installation locale, avec le domaine **annoncé**) avant tout changement, puis configure, installe et relance BIND comme pour une demande de la console. Un état refusé ne modifie rien et n'est jamais republié : la valeur d'etcd est écrasée seulement par une modification locale légitime.
- **Bascule.** `ad-sync` s'exécute avant l'alignement de rôle de `follow` : à la promotion, le nouveau primaire a déjà le keytab (si le cluster en avait un depuis plus d'une minute).
- **État pour la console.** `/run/ddibuntu/ad-sync.json` (`synced`, `published`, `applied`, `failed` + motif, sans secret), affiché sur la page « Active Directory ».
- **À vérifier au premier laboratoire** : coupure réseau réelle pendant une publication, deux administrateurs modifiant l'AD pendant une partition, principal `DNS/…` identique sur les deux nœuds avec un vrai AD.

## Itération 8 — perte de nœuds et reprise : comment c'est réalisé
- **Quorum en direct** : `quorum_json` sonde chaque pair en parallèle (`endpoint status/health`, `member list`) ; voix = membres non « learner », majorité = ⌊voix/2⌋+1, tolérance = sains − majorité. Publié dans `cluster-status.json` (`etcd.quorum`, `ca`).
- **Retrait** : `remove-node` écrit `/ddibuntu-cluster/removed/<nom>`, efface registre / version / clé Patroni, puis `member remove`. Les autres nœuds appliquent la marque dans `sync`; un nœud qui se réinscrit l'efface.
- **Reconstruction** : `recover` = sauvegarde du répertoire etcd, `force-new-cluster` à usage unique (variable `ETCD_FORCE_NEW`, jamais écrite durablement), marques de retrait pour tous les autres pairs.
- **Autorité** : `ca-sync` (minuterie `follow`) publie `/ddibuntu-cluster/ca/escrow` chiffré (gpg AES256, phrase = HMAC-SHA256 du secret ddi-xfr) et `/ddibuntu-cluster/ca/owner` ; `take-ca` la déchiffre sur un nœud de données.
- **Console** : fichier `.cluster-action` (JSON ≤ 600 octets) déposé dans le répertoire de demandes ; `ddibuntu-cluster request` (unité path) revalide tout puis publie `cluster-result.json`.

## Itération 9 — assistants de la console : comment c'est réalisé
- **Hors cluster** : l'unité `ddibuntu-cluster-setup.path` (condition : pas de `cluster.conf`) surveille `.cluster-setup` et lance `ddibuntu-cluster setup-request`. Actions : `init` (champs validés un à un, adresse du nœud vérifiée comme portée par une interface) et `join` (lot déposé à côté sous `cluster-join.bundle`, déplacé en 0600 dans l'état, détruit après usage ; `--wipe-local-db` implicite, d'où la confirmation par le nom de la machine).
- **Dans le cluster** : `bundle` est une action de plus de `.cluster-action` ; le lot est écrit en `cluster-bundle-<nom>.bundle` (0640 root:ddiconsole) et purgé après une heure par `publish_state`.
- **Phrase de passe** : tirée par la console, jamais relue ; `cmd_bundle` / `cmd_join` la prennent dans `DDI_BUNDLE_PASS` ; `last_line` la masque dans tout message publié.

## Itération 10 — sauvegardes et restauration à un instant donné : comment c'est réalisé
- **Dépôt par nœud** : `/var/lib/ddibuntu/backup` (`base/<ID>/` = `base.tar.gz`, `pg_wal.tar.gz`, `backup_manifest`, `meta.json`, `SHA256SUMS` ; `wal/*.gz`), propriété de `postgres`, plus une copie externe optionnelle (`MIRROR_DIR`). Les sauvegardes ne sont prises que **sur le primaire** ; le journal WAL est archivé par `archive_command` sur chaque nœud de données qui devient primaire (`repo_init` crée le dépôt partout dès que les sauvegardes sont activées, sans quoi l'archivage échouerait après une bascule).
- **Paramètres communs** : `ddibuntu-cluster backup-conf put|get` stocke la configuration dans etcd (`/ddibuntu-cluster/backup/config`, ≤ 1 Ko) ; `conf_push` après chaque changement, `conf_pull` au début de `auto` sur tous les nœuds ; la valeur est relue par `load_conf` (expressions régulières strictes, dans un sous-processus) et n'est appliquée que si elle diffère. Une valeur piégée est ignorée.
- **Patroni** : `render_patroni` ajoute `archive_mode: on` et `archive_command` dans la configuration dynamique et `local replication postgres peer` dans `pg_hba` ; un secondaire dont l'archivage est inactif est corrigé par le minuteur (`cluster_render` puis `patronictl restart --pending`).
- **Restauration dans le cluster** (primaire seulement) : `patronictl pause` ; arrêt de PostgreSQL ; ancien répertoire déplacé (`main.pre-restore.<date>`) ; extraction ; démarrage direct par `pg_ctl` avec les paramètres lus dans la configuration Patroni et `pg_controldata` (`cluster_pg_opts`) ; relecture des journaux jusqu'à la cible (`recovery_target_time` ou `immediate`, timeline explicite pour `--at`/`--id`, `latest` pour `--latest`) ; promotion ; arrêt ; `patronictl resume` ; `reinit` de chaque secondaire ; sauvegarde de référence. En cas d'échec : l'ancienne base est remise en place et Patroni repris. Le leader ne change pas.
- **Verrou** : un seul `flock` (`$RUNDIR/backup.lock`) protège sauvegarde, rétention et restauration ; les démons lancés pendant l'opération (PostgreSQL, Patroni) sont démarrés avec ce descripteur fermé pour ne pas conserver le verrou.
- **Console** : `.backup-request` (JSON ≤ 600 octets) déposé dans le répertoire de demandes ; `ddibuntu-backup request` (unité path) revalide tout puis publie `backup-result.json` ; l'état (`backup-status.json`) est republié par le minuteur et à chaque demande ; la phase d'une restauration est publiée dans `backup-restore.json`.
- **À vérifier au premier laboratoire** : durée de restauration et de recréation des secondaires sur une base volumineuse ; copie externe sur un vrai NFS ; restauration depuis un cluster en défaut de quorum etcd (Patroni ne peut pas être mis en pause : se reporter à `ddibuntu-cluster recover`).

## Itération 11 — alertes et supervision : comment c'est réalisé
- **Santé de nœud** : `ddibuntu-health` (root, `ddibuntu-health.timer` chaque minute, lecture seule, aucun secret) photographie les services attendus, PostgreSQL, disques, échéances de certificats, heure, charge et mémoire, et écrit `/run/ddibuntu/health.json`. Dans un cluster il dépose le même JSON par `ddibuntu-cluster health-put` dans etcd (`/ddibuntu-cluster/health/<nœud>`) : une clé par nœud, **l'arbitre compris** (il n'a ni console ni base, mais il a etcd). `health-put` refuse tout ce qui n'est pas un objet JSON de 4 Kio au plus portant le nom du nœud local ; à la relecture, `ddibuntu-cluster status` n'expose (champ `health`, 16 nœuds au plus) que les valeurs valides dont le nom égale la clé.
- **Qui évalue** : uniquement la console **accessible en écriture** (leader ou serveur seul) ; un réplica ne lance pas le moteur (`inRecovery`). En cas de bascule, le nouveau leader reprend : l'état (alertes ouvertes, silences, mémoire du dernier leader) est en base, donc répliqué. Un verrou consultatif de transaction (`pg_advisory_xact_lock(727728)`) évite tout doublon si deux consoles se croisent.
- **Évaluation** : fonction pure `evaluate(instantané, seuils, mémoire)` → constats (clé `règle|nœud|sujet`) ; `reconcile` ouvre, met à jour (gravité), puis résout après `DDI_ALERT_RESOLVE_MISSES` évaluations (2 par défaut) sans le constat. Un nœud dont la santé est périmée (plus de 180 s) n'est jugé que sur cela : pas de cascade d'alertes dérivées. `cluster.leader_changed` (information) reste ouverte une heure.
- **Notifications** : webhook et SMTP, hors du chemin d'évaluation (une panne du canal ne ralentit jamais le moteur) ; tentatives 5 fois au plus avec journal ; les silences suppriment l'envoi sans masquer l'alerte ; secrets chiffrés (AES-256-GCM, clé de la console) et jamais relus par l'API.
- **Prometheus** : `GET /api/metrics`, jeton `ddm_…` dont seule l'empreinte est stockée ; une console expose sa propre vue (à interroger sur la VIP pour suivre le leader, ou sur chaque nœud).
- **Interface** : le tableau de bord rassemble `node`, `cluster`, `backup` et `alerts` en un appel (`/api/system/dashboard`) et se rafraîchit toutes les 30 s ; l'onglet Système › Alertes gère silences, notifications, seuils et jeton.
- **À vérifier au premier laboratoire** : comportement du moteur pendant une vraie bascule du leader ; réception réelle par un serveur de messagerie et un récepteur de webhook de production ; supervision d'un arbitre dont le minuteur de santé est arrêté.

## Itération 12 — réglages du cluster, certificats, adresse d'un nœud : comment c'est réalisé
- **Réglages communs** : une clé etcd `/ddibuntu-cluster/settings` (JSON ≤ 1 Ko, **révision croissante**) porte ce qui doit être identique partout : adresse virtuelle (CIDR), VRID, réseau dédié. N'importe quel nœud de données la publie (`set-vip`, `clear-vip`, `set-net`) après avoir validé la saisie ; chaque nœud (arbitre compris) l'applique seul à sa prochaine synchronisation quand la révision publiée dépasse la sienne (`SETTINGS_REV`). Une valeur piégée dans etcd (JSON invalide, clé inconnue, type ou borne hors plage) est ignorée sans effet. **L'interface de la VIP est propre à chaque nœud** : celle du nœud si elle existe, sinon celle des réglages ; si aucune ne convient, le nœud le dit (avec la commande de correction `vip-iface`) et réessaie, sans rien casser. `set-net` est refusé si un seul nœud est hors du réseau annoncé.
- **Certificats** : la clé privée d'un nœud ne le quitte jamais. Le nœud crée clé et demande (`$PKI/renew/`, EC P-256, sujet `CN=node-<nom>` sans extension), la publie dans etcd ; **seul le nœud porteur de l'autorité signe**, et seulement une demande dont le nom est au registre, l'adresse celle du registre (ou d'un déplacement annoncé), le sujet exact, la clé EC P-256 et sans attribut ni extension ; les adresses du certificat (SAN) viennent du registre, jamais de la demande. Le certificat est déposé avec l'empreinte de la demande ; le nœud ne l'installe que s'il est signé par l'autorité, correspond à SA clé, au bon sujet et aux bonnes adresses (`cert_install` garde jusqu'à trois anciens certificats, sans clé). etcd recharge le certificat à chaque connexion : **aucun redémarrage**. Renouvellement automatique à `DDI_RENEW_DAYS` (60) jours de l'échéance, une demande à la fois, nouvelle tentative au bout d'une heure. Certificat de l'autorité : 10 ans, **non renouvelé automatiquement** (limite connue).
- **Changement d'adresse d'un nœud** (`change-ip --ip NOUVELLE --yes`, depuis le nœud) : (1) annonce `moved/<nom>` {de, vers, quand} ; (2) certificat valable pour l'ancienne **et** la nouvelle adresse ; (3) **accord des autres nœuds** : chaque autre membre sain voit l'annonce à sa synchronisation, **ouvre son pare-feu à la nouvelle adresse** (en plus de l'ancienne, uniquement si elle est dans le réseau dédié ; fichier `fw-extra`, `CLUSTER_PEERS` élargi) puis écrit un accusé `moved-ack/<nom>/<observateur>` = nouvelle adresse ; le nœud n'avance qu'après **tous** les accusés (délai `DDI_FW_WAIT`, 180 s) et annule tout, sans rien modifier, s'il en manque un (un nœud en panne s'alignera à son retour) ; un accusé signifie « mon pare-feu est ouvert maintenant » : l'observateur le retire dès que l'annonce disparaît, est annulée ou que le déplacement est terminé ; (4) `etcdctl member update` par n'importe quel membre joignable ; (5) réécriture locale (etcd, Patroni, Keepalived, pare-feu) et redémarrage d'etcd ; (6) inscription au registre. Si etcd ne répond pas sur la nouvelle adresse dans le délai (`DDI_ETCD_RESTART_WAIT`, 60 s), **retour arrière complet** (configuration, adresse du membre, annonce). Les autres nœuds s'alignent seuls (`moved_apply`) **uniquement** si l'annonce a moins d'un jour (et n'est pas datée du futur), si l'ancienne adresse est celle qu'ils connaissaient et si le registre porte bien la nouvelle : une réécriture du registre sans annonce est ignorée avec avertissement. Refus : leader PostgreSQL en place (basculer d'abord), quorum sans marge (le redémarrage d'etcd ferait tomber le quorum), adresse déjà prise, hors du réseau dédié, non portée par ce serveur.
- **Verrou de nœud** : `flock` sur `cluster.lock` (état du nœud). Les minuteries (`sync`, `follow`, `ca-sync`) ne l'attendent pas (elles reviennent à la minute suivante) ; les demandes d'un administrateur attendent leur tour (120 s, 600 s pour `request`). Sans lui, la synchronisation automatique aurait pu réécrire l'ancienne adresse pendant un changement d'adresse de plusieurs minutes. Le démon etcd lancé par les tests ne garde pas le descripteur du verrou (`8>&-`).
- **Console** : `.cluster-action` accepte `set-vip`, `clear-vip`, `vip-iface`, `set-net`, `renew-cert`, `change-ip` ; root relit le JSON (≤ 1 Ko) avec un **jeu de clés exact par action**, confirmation identique (nom du cluster ; nom du nœud pour `change-ip`), VRID entier 1–255 (booléens refusés), adresses et interfaces validées, lien symbolique refusé. L'API refuse avant dépôt ce qui est incohérent avec l'état publié (quorum, adresse d'un nœud, réseau qui exclut des nœuds, primaire, marge du quorum…). Page Cluster : cartes « Adresse virtuelle et réseau dédié », « Certificats » (jours restants, renouvellement), « Adresse de ce nœud » ; modales maison, spinner pendant l'attente du résultat de root.
- **À vérifier au premier laboratoire** : comportement de Patroni lors d'un changement d'adresse d'un nœud de données réel (redémarrage du service) ; VRRP en unicast après changement d'adresse sur un vrai réseau ; renouvellement du certificat de l'autorité (non automatisé).

## Itération 13 — test de bascule guidé : comment c'est réalisé
- **Principe** : une bascule **réelle** (`patronictl switchover`, via `ddibuntu-cluster switchover`), mesurée de bout en bout par un moniteur indépendant, puis — sur demande — le **retour au primaire d'origine**, également mesuré. Le but n'est pas de prouver que Patroni sait basculer, mais de savoir **ce que ce cluster-ci fait, en combien de temps, avant le jour où il y en a besoin**, et de garder la preuve (rapport).
- **Pré-contrôles** (`drill-check`, lecture seule, aussi lancés au début de `drill`) : au moins deux nœuds de données joignables et un seul primaire, Patroni non en pause et aucune bascule déjà planifiée, candidat = secondaire en réplication continue (jamais le primaire ni l'arbitre), retard de réplication borné (1 Mio par défaut), autres secondaires en réplication continue, aucun redémarrage en attente, quorum etcd avec voix saines, aucun autre test en cours ; Kea HA, adresse virtuelle et services des nœuds sont examinés quand ils existent (« non évalué » sinon). **Un contrôle en écart refuse le test** : aucune bascule n'est tentée et le refus est lui-même conservé comme rapport.
- **Moniteur** (`/usr/local/lib/ddibuntu/cluster-drill.py`, bibliothèque standard seulement, aucun secret lu ni écrit) : échantillonne l'API Patroni de **chaque** nœud de données (TLS mutuel avec le certificat du nœud) toutes les 0,5 s (`DDI_DRILL_POLL`) et en tire : **fenêtre sans primaire**, délai de **promotion**, délai de **rétrogradation**, **réintégration** de l'ancien primaire (réplica, même ligne de temps, en réplication continue), **rattrapage** de la réplication (retard sous 16 Kio), **ligne de temps** (doit avancer d'exactement 1), **continuité de la position WAL** (la position du nouveau primaire ne recule pas), retard maximal, puis des contrôles après coup (primaire attendu, secondaires, quorum etcd non dégradé, Kea HA, adresse virtuelle de ce nœud). Chaque mesure reçoit un verdict conforme / à surveiller / en écart selon des seuils publiés dans le rapport (fenêtre sans primaire 15 s / 30 s, promotion 30 s / 60 s, réintégration 90 s / 150 s). La **précision est celle de l'échantillonnage**, indiquée dans le rapport ; l'écriture applicative n'est pas simulée : la sonde « primaire » de Patroni fait foi.
- **Rapport** : JSON versionné (`v: 1`, ≤ 100 Ko, 150 événements horodatés au plus), conservé dans etcd sous `/ddibuntu-cluster/drills/<AAAAMMJJThhmmssZ>` (les **20 derniers**, seuls les rapports à clé valide sont comptés ou supprimés), donc **visible depuis tous les nœuds** et survivant à la perte de celui qui l'a produit ; publié pour la console dans `cluster-drills.json` (10 derniers) à chaque publication d'état. Issues : `success`, `warning` (réussi avec réserves), `failed`, `refused` (pré-contrôles).
- **Un test à la fois, la topologie ne bouge pas pendant ce temps** : verrou local (`drill.lock`) et marque `/ddibuntu-cluster/drill/active` (nœud, étape, horodatage, valable **20 minutes** ; retirée par le piège de sortie, **uniquement si elle porte l'identifiant du test**). Tant qu'elle est valable, `change-ip`, `remove-node`, `recover`, `take-ca`, `set-net` et la bascule manuelle sont refusés (le certificat et l'interface de la VIP restent permis) ; le test lance ses propres bascules avec `DDI_DRILL_RUN=1`. Un second test est refusé **sans toucher à la marque du premier**. Un nœud qui disparaît en plein test laisse une marque qui expire seule ; `drill-clear --yes` la retire tout de suite. Le verrou de nœud (`cluster.lock`) est **rendu** avant le test : la synchronisation et le suivi (Kea, BIND) continuent pendant la bascule, comme ils le feraient lors d'une vraie panne.
- **Avancement en direct** : le moniteur émet un signe de vie toutes les 3 s ; root le publie dans `cluster-drill-live.json` (étape, temps écoulé, 12 dernières étapes). La console juge le test « en cours » tant que ce signe a moins de 15 s ou que la marque etcd est valable.
- **Console** (administrateur, nœud de données qui porte le primaire — les autres consoles sont en lecture seule) : carte « Test de bascule » (historique des rapports, bouton de lancement) ; fenêtre maison en trois temps — pré-contrôles avec spinner, puis confirmation (retaper le nom du cluster, case « revenir au primaire d'origine » cochée par défaut, avertissement sur l'indisponibilité en écriture de quelques secondes), puis avancement en direct (la fenêtre peut être fermée : le test continue). Le rapport s'ouvre à la fin : mesures et verdicts par phase, contrôles après coup, chronologie des événements, seuils et précision, téléchargement en JSON. Pendant le test, la console du primaire sortant passe brièvement en lecture seule : l'interface insiste, silencieusement, jusqu'au retour du résultat.
- **Frontière de privilèges** : `.cluster-action` accepte `drill-check` (clés `action`, `node` facultatif) et `drill` (clés `action`, `confirm` = nom du cluster, `node` et `back` booléen facultatifs) ; root relit le JSON (≤ 1 Ko) avec un **jeu de clés exact**, refuse un `back` non booléen, un nom piégé, un lien symbolique, un fichier tronqué. L'API refuse avant dépôt (409) : `confirm_mismatch`, `invalid_candidate`, `quorum_required`, `cluster_state_stale`, `drill_active` ; les fichiers publiés par root sont relus champ par champ, bornés, et un statut inconnu vaut « en écart », jamais « conforme ».
- **À vérifier au premier laboratoire** : mesures sur de vrais serveurs et un vrai réseau (le test de b22 se fait en boucle locale : les temps sont ceux de Patroni, pas ceux d'un réseau) ; comportement des clients DHCP/DNS pendant la fenêtre sans primaire ; adresse virtuelle (Keepalived) suivant le primaire sur de vraies interfaces.

## Itération 14 — vues DNS : comment c'est réalisé
- **Modèle** : table `dns_views` (nom, position, `match_clients`, `match_destinations`, récursion) ; `dns_zones.view_id`. Sans vue, rien ne change. Avec vues, `named.conf.zones` contient un bloc `view "<nom>" {` par vue, dans l'ordre ; en-tête sur des lignes de forme fixe, une zone par ligne à la marge, bloc fermé par `};` (root relit ce fichier ligne à ligne).
- **Clés** : `ddi-xfr-<vue>` = HMAC-SHA256(secret `ddi-xfr`, `ddibuntu-view:<vue>`), calculée par `ddibuntu-reload` (`cluster_py bind-render`) des deux côtés : aucune distribution. Primaire : `match-clients { key "ddi-xfr-V"; !key "ddi-xfr-AUTRE"; <liste> }`, `allow-transfer` et `also-notify … key` par vue. Secondaire : `primaries { PAIR key "ddi-xfr-V"; }` et `server PAIR { keys "ddi-xfr-V"; }` dans chaque vue. Fichier `ddi-xfr-views.key` installé/retiré par `install_named`, compris dans la sauvegarde de retour arrière.
- **Contrôles** : couverture de 127.0.0.1/::1 (refus de déploiement), zones hors vue (refus du rendu), nom de vue `[a-z][a-z0-9-]{0,30}`, 16 vues au plus. Contenu déposé revalidé par root (lignes inattendues refusées).
- **À savoir** : `localhost` = toutes les adresses locales du serveur ; la source d'une requête vers sa propre adresse est cette adresse, pas 127.0.0.1.
- **À vérifier au premier laboratoire** : DDNS Kea vers une vue précise avec deux vues contenant la même zone ; `match-destinations` avec plusieurs adresses.

## Itération 15 — navigation entre nœuds, nœud préféré, connexion sur un secondaire : comment c'est réalisé
- **Nœud préféré** : clé etcd `/ddibuntu-cluster/preferred` = `{"node","at","by"}` (jeu de clés strict, séparée de `/settings` dont le format ne change pas). `ddibuntu-cluster set-preferred NOEUD | clear-preferred | preferred` ; la lecture (`preferred_read`) n'accepte qu'un nœud **de données** du registre, sinon la consigne est ignorée. Écriture exclusivement avec le quorum (`quorum_ok`, mesure en direct). Publiée dans l'état (`preferred`) par chaque nœud, arbitre compris. Le retrait d'un nœud efface sa consigne.
- **Aucun retour automatique** : Patroni garde la maîtrise du primaire ; la console compare `preferred` et le leader, signale l'écart et propose la bascule contrôlée existante (pré-contrôles inchangés).
- **Chemin console → root** : actions `set-preferred` / `clear-preferred` (zod strict, confirmation = nom du cluster, refus préalables dans `actionRefusal`), fichier `.cluster-action` relu par le validateur strict de root (jeu de clés exact).
- **Session d'un secondaire** : `r1.<charge>.<signature>`, HMAC-SHA256 avec une clé dérivée de `DDI_SECRET_KEY` (identique sur les nœuds par construction du lot d'enrôlement). Charge : utilisateur, échéance, empreinte `sha256(id|source|hachage)`. Validation à chaque requête : signature, échéance, utilisateur présent et actif, empreinte inchangée. Seules `/auth/login` et `/auth/logout` sont admises en écriture sur un secondaire.
- **Limite connue** : un jeton signé ne se révoque pas individuellement avant son échéance (4 h) ; la révocation est collective (changement de mot de passe, désactivation du compte).

## Itération 16 — mise à jour du cluster nœud par nœud : comment c'est réalisé
- **Ordre** : clé etcd `/ddibuntu-cluster/update` = `{"target","at","by"}` (jeu de clés strict, version `x.y.z`). Écrit par `update-start` (nœud de données, quorum, tous les membres etcd sains, versions de tous les nœuds connues, aucune plus récente que la cible) ; supprimé par `update-cancel` ou quand tous les nœuds sont à la cible.
- **Exécution** : `update_step`, appelée par `follow` sur chaque nœud de données (sur un arbitre, la minuterie `follow` n'est pas activée : voir « Limites et points non éprouvés »). Séquence = arbitres, secondaires, primaire (Patroni) en dernier. Un nœud agit seulement si tous ceux qui le précèdent publient la version cible (`/ddibuntu-cluster/versions/<nœud>`) ; il dépose alors `.update-request` pour `ddibuntu-selfupdate`, qui garde ses propres contrôles (signature, sauvegarde, retour arrière, garde du primaire en dernier).
- **Avancement** : chaque nœud publie `/ddibuntu-cluster/update-state/<nœud>` (waiting, requested, updating, done, failed) ; l'état publié (`update`) porte ordre, versions et avancement.
- **Sûreté** : un échec (état `failed` de selfupdate pour la cible, postérieur à l'ordre) suspend la file ; pas de nouvelle tentative automatique. Un nœud absent ou malsain empêche de démarrer ; s'il tombe en cours de route, la file attend (priorité à l'homogénéité).

## Itération 17 — la PKI (EJBCA) suit le leader : comment c'est réalisé
- **Principe** : un seul EJBCA, sur le leader Patroni ; la base `ejbca` est répliquée comme les autres bases. Tout le reste de l'état de la PKI (secrets, instance, clé de récupération, consigne d'arrêt, métadonnées des autorités, volume) est un **paquet unique chiffré** dans la clé etcd `/ddibuntu-cluster/pki/state` ; sans les secrets de `ejbca.env`, les clés des autorités de la base ne se déchiffrent pas.
- **Qui fait quoi** : `follow` (minuterie d'une minute, verrou du cluster) → `pki-sync` (publie ou applique, selon les trois voies L / E / S) puis, en interne, l'alignement du rôle (`ddibuntu-pki align leader|replica`). Le démarrage de la machine ne lance jamais la PKI dans un cluster (l'unité n'a pas de `[Install]`) : seul l'alignement la démarre, et seulement sur le leader.
- **Chiffrement** : GPG AES-256, phrase = HMAC-SHA256 du secret d'échange `ddi-xfr` avec `ddibuntu-pki-state-v1`. L'arbitre (etcd seul, sans ce secret) ne peut pas lire le paquet ; la console et le statut du cluster ne reçoivent que l'empreinte (12 caractères), l'auteur et la date.
- **Autres clés etcd** : `/ddibuntu-cluster/pki/updating` (marque de mise à jour en cours, *put-if-absent*) et `/ddibuntu-cluster/pki/nodes/<nœud>` (état de préparation de chaque nœud de données : rôle, unité, image, version, consigne, empreinte synchronisée ; écrit à chaque changement ou toutes les 10 minutes). `remove-node` supprime la clé du nœud retiré.
- **Bascule** : Patroni promeut un secondaire ; au passage suivant de `follow` (une minute au plus), l'ancien leader arrête EJBCA et le nouveau le démarre sur la base répliquée (démarrage mesuré 72 à 126 s). L'image et l'unité étaient déjà prêtes. `pki.<domaine>` doit désigner l'adresse virtuelle.
- **Sûretés** : arrêt volontaire répliqué (`desired`) ; marque de mise à jour interrompue (aucun démarrage tant qu'elle n'est pas levée à la main) ; etcd illisible = pas de démarrage (`cluster-unreachable`) ; état altéré, d'une autre clé, aux chemins hostiles ou trop gros refusé avant tout effet ; un secondaire ne publie jamais ; deux états différents au premier contact = conflit signalé, rien d'écrasé.
- **Limites connues** : pas d'actif-actif (2 à 3 minutes sans PKI à chaque bascule : CRL et SCEP injoignables, certificats déjà émis valables) ; le point de retour d'une mise à jour reste sur le nœud qui l'a pris ; l'arbitre n'héberge pas la PKI ; pas d'alerte dédiée (la carte de la page PKI affiche blocages et conflits).
- **Tests** : `tests/b40-pki-cluster-live.sh` (3 nœuds simulés, vrai etcd), `tests/b41-pki-cluster-state-live.sh` (vrai conteneur EJBCA), `webui/tests/unit-pki-cluster.test.ts`, `webui/tests/e2e-iter57.test.ts`.

## Itération 18 — RADIUS suit le leader (actif / passif) : comment c'est réalisé
- **Principe** : un seul FreeRADIUS, sur le leader PostgreSQL, derrière l'adresse virtuelle (Keepalived ne la porte que sur le leader). Pas d'actif / actif : un échange EAP doit rester sur le même serveur, et la configuration (secrets, clés, règles) ne se duplique pas sur un second nœud.
- **Source de vérité** : la base répliquée (réglages et secrets chiffrés par `DDI_SECRET_KEY`, la même sur tous les nœuds). Rien ne voyage dans etcd, contrairement à la PKI.
- **Root** : `follow` (une minute) appelle `ddibuntu-radius align leader|replica`. Sur un secondaire : service arrêté et désactivé. Toute demande de la console (`apply`, `stop`, `crl`) est refusée sur un nœud qui n'est pas leader (`standalone` est accepté : hors cluster, rien ne change).
- **Console** : le réglage `radius_snapshot` garde la dernière demande « apply » **acceptée par root** (chiffrée) ; la tâche `radius-follow` du leader la rejoue quand le service ne tourne pas (état publié par root), au plus toutes les 5 minutes. Un arrêt voulu efface l'instantané.
- **Bascule** : adresse virtuelle en quelques secondes ; l'ancien leader arrête RADIUS au passage suivant de `follow` ; le nouveau le démarre par la reprise de la console : **1 à 2 minutes** sans réponse pour les nouvelles authentifications.
- **Limites** : bascule réelle non essayée ; journal propre à chaque nœud ; pare-feu RADIUS posé là où le déploiement s'exécute.
